FP8 RL in verl                                        *verl-low_precision-fp8*

Last updated: 11/02/2026

verl supports two FP8 modes for accelerating RL training:

Mode                     Training Precision           Rollout Precision
-----------------------  ---------------------------  ------------------------
FP8 Rollout Only         BF16                         FP8
FP8 End-to-End           FP8 (Megatron)               FP8 (vLLM)

  [!TIP] For ready-to-run scripts, see the low-precision recipe directory
  https://github.com/verl-project/verl-recipe/tree/main/low_precision.

 * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * * *

FP8 ROLLOUT ONLY                          *low_precision-fp8-fp8-rollout-only*

FP8 rollout-only mode keeps training in BF16 and quantizes rollout inference
to FP8. This reduces GPU memory during generation and speeds up rollout
without affecting training precision.

Implementation                              *low_precision-fp8-implementation*

The rollout engine starts from a compressed-tensors `quantization_config`
with dummy weights, and the trainer quantizes every weight sync to that
config with the compressed-tensors compressors
(`verl/utils/qat/compressed_tensors.py`). On the vLLM side we monkey patch
`process_weights_after_loading` of the compressed-tensors FP8 linear/MoE
methods so refits are written back into the live parameters
(`verl/utils/vllm/vllm_fp8_utils.py`).

Support Matrix                              *low_precision-fp8-support-matrix*

- FP8 blockwise quantization for rollout (compressed-tensors preset
  `FP8_BLOCK`)

  - Used in Deepseek, which is 1x128 quantization for activations and
    128x128 quantization for model weights

- Dense models and MoE models
- Async rollout interfaces
- vLLM or SGLang rollout (SGLang validated on Hopper only) with the Megatron
  training backend; TRT-LLM and FSDP are not supported

Usage                                                *low_precision-fp8-usage*

Enable in config file:

>yaml
    rollout:
      quantization:
        linear: FP8_BLOCK  # dense linear layers (attention, dense MLP, shared experts)
        moe: FP8_BLOCK     # routed experts
        ignore: []         # extra "re:" patterns kept in BF16
<
Or via command line:

>python
    actor_rollout_ref.rollout.quantization.linear=FP8_BLOCK \
    actor_rollout_ref.rollout.quantization.moe=FP8_BLOCK
<
Routers, `lm_head`, embeddings, vision towers and MTP layers stay in BF16 by
default, as do layers whose weight shape is not a multiple of the 128x128
block. To provide a complete compressed-tensors `quantization_config`
instead, set
`actor_rollout_ref.rollout.quantization.config_file=/path/to/quantization_config.json`
(exclusive with `linear` / `moe` / `ignore`).

                           *low_precision-fp8-fp8-end-to-end-training-rollout*
FP8 END-TO-END (TRAINING + ROLLOUT)

FP8 E2E applies FP8 to the entire RL pipeline: forward/backward passes via
Transformer Engine, FP8 optimizer states, and FP8 rollout inference via
vLLM. This maximizes memory savings and throughput.

Requirements                                  *low_precision-fp8-requirements*

- CUDA 12.9+ (required for block-wise FP8 scaling)
- Transformer Engine with block-wise FP8 support
- Environment variable: `NVTE_FP8_BLOCK_SCALING_FP32_SCALES=1`, on Hopper
  only. Do not set it on Blackwell (SM100+): there Transformer Engine runs
  block-wise scaling through MXFP8 GEMMs, whose E8M0 scales hold only an
  exponent, so it requires power-of-two block scales and stops at the first
  FP8 quantization with
  `Assertion failed: pow2_scale ... requires using power of two scaling factors`
  when the variable is set (see #6172
  https://github.com/verl-project/verl/issues/6172). Leaving it unset gives
  power-of-two scales, the Transformer Engine default.

Key Configuration                        *low_precision-fp8-key-configuration*

>yaml
    # FP8 training via Transformer Engine
    actor_rollout_ref.actor.megatron.override_transformer_config:
      fp8: "hybrid"              # FP8 forward + backward; also supports "e4m3"
      fp8_recipe: "blockwise"    # block-wise scaling

    # FP8 optimizer
    actor_rollout_ref.actor.optim.override_optimizer_config:
      fp8_recipe: "blockwise"

    # FP8 rollout inference (vLLM)
    actor_rollout_ref.rollout.quantization:
      linear: FP8_BLOCK
      moe: FP8_BLOCK
<

FP8 KV Cache (Optional)              *low_precision-fp8-fp8-kv-cache-optional*

The rollout KV cache can also be stored in FP8 by passing vLLM's
`kv_cache_dtype` through `engine_kwargs`:

>bash
    +actor_rollout_ref.rollout.engine_kwargs.vllm.kv_cache_dtype=fp8_e4m3
<
- Only the rollout side changes. Training-side core attention stays in BF16,
  so the extra train/rollout mismatch is corrected by TIS like the rest of
  the FP8 rollout error.
- The q/k/v scales are uncalibrated (1.0): verl does not export KV cache
  scales, so the values are cast to FP8 directly. On Hopper, vLLM's
  FlashAttention-3 backend then runs attention in FP8 and quantizes Q as
  well.
- Combined with `quantization.linear/moe=FP8_BLOCK`, this needs #8483
  https://github.com/verl-project/verl/pull/8483. Without it, the attention
  scales keep the random values from the dummy load and the rollout
  generates garbage.
- Validated with vLLM only.

Support Matrix                                         *low_precision-fp8-id1*

- Megatron training backend (via Megatron-Bridge)
- Verified on Qwen3-30B-A3B and Qwen3-8B (H100); Qwen3-30B-A3B also on H20
- Block-wise FP8 scaling (`fp8_recipe: "blockwise"`)
- Optional FP8 KV cache in vLLM rollout

Experiments and Results            *low_precision-fp8-experiments-and-results*

Qwen3-30B-A3B MoE Model            *low_precision-fp8-qwen3-30b-a3b-moe-model*

Configuration

- DAPO recipe. AIME24 online validation.
- Megatron + Megatron-Bridge, FP8 async rollout with vLLM
- MoE router in BF16 for both vLLM and Megatron-Core
- Prompt batch size 128, n=16
- Max response length 20K
- Token-level TIS, C=2
- 2*8*H100, CUDA 12.9

Orange: BF16, Green: FP8 E2E, Red: FP8 rollout + BF16 training

Results and observations:

- FP8 E2E achieves comparable accuracy to the BF16 baseline, with the two
  curves closely aligned throughout training.
- The training/inference precision mismatch (measured by KL divergence)
  follows the ordering: FP8 rollout-only > FP8 E2E > BF16 E2E. This is
  expected, as FP8 E2E maintains consistent precision across both training
  and inference, resulting in lower distribution mismatch than the FP8
  rollout-only setting where training remains in BF16.

MXFP4 MoE QAT on Blackwell                      *verl-low_precision-mxfp4_qat*

Last updated: 11/06/2026

MXFP4 is the OCP microscaling FP4 format: E2M1 elements with one E8M0 scale
per 32-element block. In verl it covers the routed experts of MoE models.
The rollout serves MXFP4 expert weights, quantized on the trainer side, and
DeepGEMM quantizes the expert activations to FP8 at run time. Transformer
Engine has no MXFP4 training, so training stays in BF16; with QAT, the
routed experts are fake-quantized during training: their weights exactly as
the exported rollout weights, their inputs to MXFP8, close to the rollout's
FP8 activations.

The rollout quantization interface shared by all formats, the kernel
defaults and the format details are described in |verl-low_precision-qat|.
For MXFP8 end to end, see |verl-low_precision-mxfp8|.

REQUIREMENTS                            *low_precision-mxfp4_qat-requirements*

- Blackwell GPUs for the rollout: the MXFP4-weight × FP8-activation experts
  are served by vLLM's DeepGEMM FP4 MoE kernel (SM100/SM120). Hopper has no
  such kernel and is outside this recipe; see |verl-low_precision-qat|.
- Training: the Megatron-Bridge model path; QAT uses NVIDIA ModelOpt.
- Rollout: vLLM (the version verl locks).

CONFIGURATION                          *low_precision-mxfp4_qat-configuration*

>yaml
    # MXFP4 rollout experts; dense layers stay in BF16
    actor_rollout_ref.rollout.quantization:
      linear: null
      moe: MXFP4

    # optional: MXFP4 QAT on the routed experts
    actor_rollout_ref.actor.megatron.qat:
      enable: True
      mode: mxfp4        # mxfp4_mxfp8 also trains the dense layers with MXFP8 QAT (vLLM: linear: MXFP8)
<
Notes:

- `lm_head`, the token embedding, MoE routers and every dense layer stay in
  BF16 on the rollout and in training.
- ModelOpt installs the fake quantizers; they run verl's TileLang MXFP4
  kernel, the one the trainer-side exporter uses without dequantization, so
  the QAT forward and the exported rollout weights agree bit for bit (see
  |verl-low_precision-qat|). The experts' inputs are fake-quantized to MXFP8
  (1x32 blocks), while the rollout's DeepGEMM kernel quantizes them to FP8
  in 1x128 groups with E8M0 scales.
- QAT quantizes the Transformer Engine modules of the layer spec that
  Megatron-Bridge builds for the model, the grouped expert linears included,
  so tensor and expert parallelism can be combined. All expert weights of a
  grouped linear are fake-quantized in one kernel launch.
- QAT and Transformer Engine FP8 training are mutually exclusive; the engine
  refuses the combination.

MXFP8 RL on Blackwell                               *verl-low_precision-mxfp8*

Last updated: 10/22/2026

MXFP8 is the OCP microscaling FP8 format: E4M3 elements with one E8M0 scale
per 32-element block, decoded natively by Blackwell tensor cores. This
recipe trains with Transformer Engine's MXFP8 recipe and serves the rollout
in MXFP8, with the rollout's weights quantized on the trainer side with the
learner's block rule.

For FP8 on Hopper (the `blockwise` recipe), see |verl-low_precision-fp8|.
The rollout quantization interface shared by all formats, and the vLLM and
SGLang specifics, are described in |verl-low_precision-qat|.

REQUIREMENTS                                *low_precision-mxfp8-requirements*

- Blackwell GPUs (SM100+)
- Training: Megatron-Core >= 0.13 and Transformer Engine >= 2.1, on the
  Megatron-Bridge model path
- Rollout: vLLM 0.29 or SGLang 0.5.20 (the versions verl locks)

CONFIGURATION                              *low_precision-mxfp8-configuration*

>yaml
    # MXFP8 training via Transformer Engine
    actor_rollout_ref.actor.megatron.override_transformer_config:
      fp8: "e4m3"                # element format; "hybrid" (e4m3 fwd + e5m2 bwd) also supported
      fp8_recipe: "mxfp8"        # 32-element block scaling

    # MXFP8 rollout
    actor_rollout_ref.rollout.quantization:
      linear: MXFP8
      moe: MXFP8
<
Notes:

- Weights stay in BF16 (`fp8_param` is not supported); only the GEMM inputs
  are cast to MXFP8, so checkpoints are unchanged.
- With `fp8_recipe: "mxfp8"`, verl pads packed sequences to the 32-token
  blocks MXFP8 needs.
- QAT and Transformer Engine FP8 training are mutually exclusive; the engine
  refuses the combination.
- `lm_head`, the token embedding and MoE routers stay in BF16 on the
  rollout, as in training. Further layers can be kept in BF16 with
  `rollout.quantization.ignore`.
- Given the same BF16 weight, the trainer-side exporter (compressed-tensors)
  and Transformer Engine pick the same E8M0 scale for every block except
  those whose amax is exactly `448 * 2**k`, where compressed-tensors picks
  the next one up; in such a block only elements below `amax / 14336`
  dequantize differently, by at most about `4.4e-6 * amax`. This compares
  the weight quantizers only, not activations, reduction order or the KV
  cache.

ROLLOUT KERNELS                          *low_precision-mxfp8-rollout-kernels*

verl defaults the MXFP8 dense and MoE kernels of vLLM and SGLang to
DeepGEMM; for details, see |verl-low_precision-qat|.

https://github.com/verl-project/verl/blob/main/examples/mxfp8/run_qwen3_8b_megatron.sh
runs GRPO on Qwen3-8B with GSM8K, MXFP8 end to end; `PRECISION=bf16` runs

Configuration

NVFP4 RL on Blackwell                               *verl-low_precision-nvfp4*

Last updated: 11/02/2026

This recipe trains the routed experts of an MoE model in real NVFP4 with
Megatron and Transformer Engine, and serves the rollout in the same
precision. Activations are quantized per token on both sides. Parameters
stay BF16; attention, dense MLPs, shared experts, router, norms, embeddings
and the LM head run in BF16.

For NVFP4 fake-quantization training, see the NVFP4 QAT section of
|verl-low_precision-qat|, which also describes the rollout quantization
interface shared by all formats.

REQUIREMENTS                                *low_precision-nvfp4-requirements*

- Blackwell (SM100) GPUs
- Validated with PyTorch 2.13 / CUDA 13, Transformer Engine 2.20.2,
  Megatron-Core 0.19.2, Megatron-Bridge 0.6.2 and vLLM 0.32.0
  (`uv sync --frozen --extra megatron --extra vllm`)
- Megatron backend, PP=1 without virtual pipeline parallelism
- vLLM rollout with TP and EP=1 or EP=TP, the colocated `naive` checkpoint
  engine and `FULL_DECODE_ONLY` CUDA graphs. Data-parallel EP, EPLB, context
  parallelism (DCP/PCP) and speculative decoding are not supported.

CONFIGURATION                              *low_precision-nvfp4-configuration*

>yaml
    actor_rollout_ref:
      actor:
        megatron:
          override_transformer_config:
            fp4: e2m1
            fp4_recipe: nvfp4
            first_last_layers_bf16: true
            num_layers_at_start_in_bf16: 2   # whole decoder layers kept in BF16
            num_layers_at_end_in_bf16: 4

<
- `fp4` applies only to the routed experts and cannot be combined with
  `qat`. Training quantizes their activations per token in the forward pass
  and runs the backward GEMMs on the dequantized forward operands;
  `NVTE_BACKWARD_OVERRIDE=high_precision` uses the BF16 operands instead.
- The rollout must keep exactly the training BF16 layers; the trainer checks
  every exported expert weight against them.
- Transformer Engine reads its NVFP4 recipe from `NVTE_*` environment
  variables; the trainer rejects a recipe that differs. See
  `examples/real_nvfp4/runtime_env.yaml`.
- Routed experts are found by name, so the recipe is not tied to one
  architecture. It is validated on Qwen3-30B-A3B, Qwen3.5-35B-A3B and a
  small model with the DeepSeek-V3 layout (dense first layer, MLA, shared
  expert).

ROLLOUT                                          *low_precision-nvfp4-rollout*

`moe: NVFP4` runs with `moe_activation: nvfp4_per_token` (vLLM's
`quantization_config.moe.activation`), the default. It exports NVFP4 expert
weights on the trainer side, bit-identical to vLLM's online
`nvfp4_per_token` quantization, and runs them on FlashInfer's TRT-LLM MoE
kernel with per-token activation scales. Refits load each bucket in place
into the storage the CUDA graphs captured, so the extra memory is one MoE
layer's post-processing. With rollout TP and EP off, each rank holds a slice
of every expert and computes the per-token scale of the `down_proj` input
over its slice, so results differ slightly from TP=1.

Low-Precision Rollout and Quantization-Aware Training *verl-low_precision-qat*

Last updated: 11/2/2026

In RL training, rollout usually dominates the step time, and for large MoE
models it is bound by memory capacity and bandwidth. Running rollout in low
precision:

- shrinks weight memory, leaving more room for KV cache and higher
  concurrency;
- reduces memory traffic during decode, improving throughput;
- uses FP8/FP4 Tensor Cores on Hopper/Blackwell to speed up prefill.

The cost is a numerical gap between the high-precision trainer and the
low-precision rollout (training-inference mismatch). It makes importance
sampling and off-policy correction less accurate and, in bad cases,
destabilizes training. Quantization-Aware Training (QAT) narrows this gap by
training the model against the same quantization the rollout uses.

                           *low_precision-qat-background-model-weight-formats*
BACKGROUND: MODEL WEIGHT FORMATS

HuggingFace checkpoints come in two flavors:

1. High precision: BF16 weights, no `quantization_config` in `config.json`.
2. Low precision: `config.json` carries a `quantization_config` describing
   how each layer is quantized. Models often use different formats for
   linear layers (attention, dense MLP, shared experts) and MoE (routed
   experts).

The trainer always trains in high precision; low-precision checkpoints are
dequantized before training. The rollout uses the model's own
`quantization_config` if it has one; a BF16 model can run rollout in BF16
or, for higher throughput, in low precision through `rollout.quantization`.

HOW IT WORKS                                  *low_precision-qat-how-it-works*

- Trainer: always trains in high precision (BF16). With QAT enabled, the
  forward pass uses fake-quantized weights (quantize then dequantize) and
  gradients flow through a straight-through estimator.
- Rollout: the inference engine starts with dummy weights and either the
  model's native `quantization_config` or a `rollout.quantization` override.
  It allocates parameters as if it were loading that low-precision
  checkpoint (for example FP8 `weight` + `weight_scale_inv`).
- Weight refit export: the training backend first exports weights under
  canonical HuggingFace names. A trainer-side `WeightQuantizer`, selected
  from the effective rollout `quantization_config`, converts each sync
  bucket into exactly the checkpoint tensors expected by the rollout engine.
  Standard native FP8 is quantized to the `Fp8Config` layout; native and
  overridden compressed-tensors configs use the same compressed-tensors
  exporter. FP8_BLOCK, MXFP8 and MXFP4 use the same TileLang quantize/pack
  kernels as QAT, while NVFP4 retains its global-scale-aware
  compressed-tensors path. DeepSeek-V4 is already quantized by
  Megatron-Bridge, so its exporter only normalizes the packed byte dtype.
  The rollout worker therefore loads pre-quantized tensors and is not
  responsible for quantization.

This exporter/loader boundary is intended to decouple the two sides. The
target architecture is the Cartesian product of training backends
`[Megatron, VeOmni, TorchTitan]` and rollout engines `[vLLM, SGLang]`: each
trainer exports canonical named tensors, each `WeightQuantizer` defines a
checkpoint wire format, and each rollout engine only implements
loading/refit for that format. The support matrix below records the
combinations currently validated; it does not imply that the full target
matrix is implemented yet.

For an override-based rollout, the HuggingFace checkpoint stays in BF16; no
offline quantization or calibration step is needed. The override format is
described using the open compressed-tensors
https://github.com/neuralmagic/compressed-tensors schema, which can express
different schemes for linear and routed MoE layers.

The trainer must be Megatron (FSDP is not yet supported for this feature).
The rollout engine can be vLLM or SGLang; TRT-LLM raises an error if

for which vLLM 0.29 has no DeepGEMM kernel, and NVFP4, for which neither

MXFP4 and NVFP4 support is scoped to routed experts. Both engines support

scope. verl's `MXFP4` checkpoint preset stores MXFP4 expert weights with
group size 32 and E8M0 scales. DeepGEMM dynamically quantizes their expert
activations to FP8 with group size 128; the training-side MXFP4 mode uses
the same runtime recipe. This differs from compressed-tensors' `MXFP4`
preset, which is W4A4, and from vLLM's native `Mxfp4Config`, whose
checkpoint format is nominally W4A16.

CONFIGURATION                                *low_precision-qat-configuration*

Rollout quantization                  *low_precision-qat-rollout-quantization*

>yaml
    actor_rollout_ref:
      rollout:
        quantization:
          linear: FP8_BLOCK   # attention, dense MLP, shared experts
          moe: FP8_BLOCK      # routed experts
          ignore: []          # extra layers kept in BF16: exact names or "re:<regex>"
          config_file: null   # path to a compressed-tensors quantization_config JSON
<
- When `linear`, `moe` and `config_file` are all `null` (the default), the
  rollout runs in the model's native precision.
- `linear` and `moe` can be set independently. Setting one of them to `null`
  keeps those layers in BF16, e.g. `linear: null, moe: FP8_BLOCK` quantizes
  only the routed experts.
- `MXFP4` and `NVFP4` are valid only for `moe`. Use `linear: null` for BF16
  dense layers. `NVFP4` always quantizes expert activations per token
  (`moe_activation: nvfp4_per_token`, the default). vLLM also supports
  `linear: MXFP8, moe: MXFP4`; that mixed override is not supported by
  SGLang.
- The following layers are always kept in BF16: `lm_head`, embeddings, MoE
  routers (`mlp.gate`, `shared_expert_gate`), vision towers and MTP layers.
- `ignore` adds more layers on top of these, using HuggingFace layer names.
  Layers incompatible with the selected scheme are not detected
  automatically: list them explicitly. For example, MXFP8 on Qwen3.5
  requires `["re:.*linear_attn\\.in_proj_[ab]$"]` because these projections
  are too small for the vLLM kernel.
- For an all-MXFP8 SGLang rollout, regex ignores must have a known SGLang
  module-name translation. Use an exact SGLang module name for other
  ignores; unsupported regex patterns are rejected before launch.

From the command line:

>python
    actor_rollout_ref.rollout.quantization.linear=FP8_BLOCK \
    actor_rollout_ref.rollout.quantization.moe=FP8_BLOCK
<
For Qwen3.5 MXFP8:

>python
    actor_rollout_ref.rollout.quantization.linear=MXFP8 \
    actor_rollout_ref.rollout.quantization.moe=MXFP8 \
    'actor_rollout_ref.rollout.quantization.ignore=["re:.*linear_attn\\.in_proj_[ab]$"]'
<

Custom `quantization_config`    *low_precision-qat-custom-quantization-config*

For full control, point `config_file` at a compressed-tensors
`quantization_config`. It can be either the `quantization_config` object
itself or a HuggingFace `config.json` that contains one. `config_file`
cannot be combined with `linear`, `moe` or `ignore`, and it is used as-is
(the default ignore list is not added). Every config group must numerically
match a supported preset.

Example equivalent to `linear: FP8_BLOCK, moe: FP8_BLOCK` for Qwen3.5:

>json
    {
      "quant_method": "compressed-tensors",
      "format": "float-quantized",
      "config_groups": {
        "group_0": {
          "targets": ["Linear"],
          "weights": {"num_bits": 8, "type": "float", "symmetric": true,
                      "strategy": "block", "block_structure": [128, 128], "dynamic": false},
          "input_activations": {"num_bits": 8, "type": "float", "symmetric": true,
                                "strategy": "group", "group_size": 128, "dynamic": true},
          "format": "float-quantized"
        }
      },
      "ignore": [
        "re:.*lm_head$", "re:.*embed_tokens$", "re:.*visual\\..*", "re:^mtp\\..*",
        "re:.*mlp\\.gate$", "re:.*shared_expert_gate$",
        "re:.*linear_attn\\.in_proj_a$", "re:.*linear_attn\\.in_proj_b$"
      ]
    }
<

QAT (Megatron)                                *low_precision-qat-qat-megatron*

QAT is optional. Enable it on the actor and pick the mode that matches the
rollout preset:

>yaml
    actor_rollout_ref:
      actor:
        megatron:
          qat:
            enable: true
            mode: fp8   # FP8_BLOCK -> fp8, MXFP8 -> mxfp8, MXFP4 -> mxfp4, NVFP4 -> nvfp4
<
QAT requires a quantized rollout: set `rollout.quantization` or use a
checkpoint with a native `quantization_config` that verl supports for export
and refit. verl checks at startup that the QAT mode matches the effective
rollout configuration. Megatron QAT uses NVIDIA ModelOpt
https://github.com/NVIDIA/Model-Optimizer to install and dispatch fake
quantizers. FP8_BLOCK, MXFP8 and MXFP4 dispatch to verl's TileLang kernels
with fused quantize-dequantize and straight-through gradients; parameter
export invokes the same kernels without dequantization, making their
quantized values and scales bit-exact by construction. NVFP4 is described
below. Both FP4 modes apply only to routed experts. MXFP8 and MXFP4 generate
E8M0 scales with DeepSeek's upward power-of-two rounding recipe. MXFP4
expert activations use the MXFP8 1x32 kernel rather than FP4. Use
`mxfp4_mxfp8` for the vLLM combination where dense linear layers also use
MXFP8. Its `ignore_patterns` use Megatron module names and `fnmatch` syntax.
Keep them aligned with the rollout ignore list; for Qwen3.5 MXFP8, add
`*linear_attn.in_proj_a` and `*linear_attn.in_proj_b`.

NVFP4 QAT                                        *low_precision-qat-nvfp4-qat*

`mode: nvfp4` with `rollout.quantization.moe: NVFP4` trains W4A4 routed
experts against the rollout that |verl-low_precision-nvfp4| uses, with the
same requirements and expert tensor parallel size 1.

- Weights: E2M1 values in groups of 16 with E4M3 scales and one global scale
  per expert matrix; `gate_proj` and `up_proj` share one. Fake quantization
  and the trainer-side export run the same kernel, so the rollout gets the
  weights training used.
- Activations: each token gets a global scale from its own amax, as in the
  rollout's MoE kernel. Fake quantization matches FlashInfer's per-token
  quantization bitwise, including `FLASHINFER_DISABLE_FP4_QUANT_FAST_MATH`;
  set it the same way for the trainer and the rollout. The rollout quantizes
  the `down_proj` input inside the fused kernel, so that input matches only
  approximately.

Engine notes                                  *low_precision-qat-engine-notes*

- vLLM: quantized FP8/MXFP8/MXFP4 rollouts default to
  `linear_backend=deep_gemm` and `moe_backend=deep_gemm` when those options
  are omitted. Set either option under `engine_kwargs.vllm` to override it
  independently. MXFP8 Linear falls back as noted above, while the MXFP4
  preset has BF16 dense layers. Hopper FP8 block configs with FP32 scales
  explicitly disable DeepGEMM E8M0; all other cases retain vLLM's
  architecture-specific default. On AMD ROCm, which has no DeepGEMM, verl
  sets neither option and vLLM selects its AITER or Triton kernels.
- SGLang: quantized FP8/MXFP8/MXFP4 rollouts similarly default
  `fp8_gemm_runner_backend` and `moe_runner_backend` to `deep_gemm`.
  Explicit values under `engine_kwargs.sglang` take precedence.
- vLLM MXFP4: vLLM 0.29's compressed-tensors path otherwise ignores the
  requested expert activation scheme. verl routes MXFP4 experts through the
  DeepGEMM FP4 backend, whose dynamic FP8 activations use group size 128.
- vLLM NVFP4: verl supports only W4A4 routed experts with per-token
  activations on FlashInfer TRT-LLM. W4A16, static activation scales, dense
  NVFP4 and other MoE backends are rejected.

EXAMPLE                                            *low_precision-qat-example*

Qwen3.5-35B-A3B on 8 GPUs with FP8 block rollout and FP8 QAT:

>bash
    python3 -m verl.trainer.main_ppo \
        model_engine=megatron \
        actor_rollout_ref.model.path=Qwen/Qwen3.5-35B-A3B \

        actor_rollout_ref.actor.megatron.qat.enable=True \
        actor_rollout_ref.actor.megatron.qat.mode=fp8 \
        actor_rollout_ref.rollout.name=vllm \
        actor_rollout_ref.rollout.quantization.linear=FP8_BLOCK \
        actor_rollout_ref.rollout.quantization.moe=FP8_BLOCK \
        ...
<

MEASURING THE MISMATCH              *low_precision-qat-measuring-the-mismatch*

`scripts/rollout_logprob_diff.py` runs one rollout, recomputes the log-probs
with the Megatron actor, and reports the gap (`kl`, `k3_kl`, absolute
log-prob difference, etc.). Use it to check a configuration before a long
run:

>bash
    python scripts/rollout_logprob_diff.py --model-path ~/models/Qwen3.5-35B-A3B --ep 8 \
        --quant-linear FP8_BLOCK --quant-moe FP8_BLOCK \
        --quant-ignore 're:.*linear_attn\.in_proj_[ab]$' \
        --qat-mode fp8 \
        --qat-ignore '*linear_attn.in_proj_a' --qat-ignore '*linear_attn.in_proj_b' \
        --r3-router-replay
<

LIMITATIONS                                    *low_precision-qat-limitations*

- SGLang MXFP8 and MXFP4 custom refit requires the default bucketed weight
  sync so all derived kernel layouts can be rebuilt after the final bucket.
  The checkpoint engine's `delta_flush` wire format is not supported.
- Native vLLM `Fp8Config` rollout is supported without a rollout override.
  Standard 128x128 block-FP8 models are quantized by the trainer-side
  exporter; DeepSeek-V4 keeps the private mixed FP8/FP4 layout already
  exported by Megatron-Bridge.
- Megatron QAT and the rollout use separate ignore lists and naming
  conventions. Users must keep them aligned.
