Async Reinforcement Learning                    *vllm-training-async_rl-index*

OVERVIEW                                    *training-async_rl-index-overview*

In a standard RL training loop, generation and training happen sequentially:
the policy generates rollouts, then training runs on those rollouts, and the
cycle repeats. During generation the training accelerators sit idle, and
vice versa.

The one-off pipelining approach separates the generation and training phases
into two parallel coroutines, allowing the model to generate new samples
while simultaneously training on previously generated data. This can lead to
better GPU utilization and greater training throughput.

However, this overlap introduces a complication: weights must be updated in
the inference engine mid-flight, while requests may still be in progress.

THE PAUSE AND RESUME API    *training-async_rl-index-the-pause-and-resume-api*

To safely update weights while the inference engine is running, vLLM
provides `pause_generation` and `resume_generation` methods. These let the
trainer coordinate a clean window for weight synchronization without losing
in-flight work.

pause_generation                    *training-async_rl-index-pause_generation*

>python
    await engine.pause_generation(mode="keep", clear_cache=True)
<
The `mode` parameter controls how in-flight requests are handled, and
whether new requests are admitted while paused:

Mode     In-flight requests                 New requests
-------  ---------------------------------  ----------------------------------
"abort"  Aborted immediately, returning     Rejected with HTTP 503 until
         partial results (default)          resume
"wait"   Running requests finish before     Rejected with HTTP 503 until
         the pause completes; queued ones   resume
         run after resume
"keep"   Frozen in the queue; they resume   Accepted and queued
         when resume_generation is called

`"abort"` and `"wait"` treat the pause as a generation boundary: from the
moment the pause starts (for `"wait"`, including while in-flight requests
drain) until `resume_generation` returns, the engine rejects new requests
from every API server rather than carrying them across the boundary. Clients
should retry on 503. A request racing the pause call itself may instead be
treated as in-flight, and input to an already-open streaming-input session
is still accepted. Other pauses, such as `sleep`, keep queueing new
requests.

The `clear_cache` parameter controls whether to clear the KV cache and
prefix cache after pausing.

`clear_cache=True` also resets a configured KV connector's cache. To clear
only the local caches, pause with `clear_cache=False`, then call
`reset_prefix_cache(reset_running_requests=True, reset_connector=False)`.
Block hashes do not cover the weights, so keep the connector's cache only if
the weights do not change, or give requests a `cache_salt` per weight
version.

resume_generation                  *training-async_rl-index-resume_generation*

>python
    await engine.resume_generation()
<
Resumes the scheduler after a pause. Any requests frozen with `mode="keep"`
will continue generating.

Wait for `pause_generation()` to finish before resuming, since a
data-parallel MoE engine can reject an early resume. Once generation
resumes, calling `resume_generation()` again has no effect.

HTTP Endpoints                        *training-async_rl-index-http-endpoints*

With `VLLM_SERVER_DEV_MODE=1`, the vLLM HTTP server exposes the same
functionality via:

- `POST /pause?mode=keep` - Pause generation
- `POST /resume` - Resume generation
- `POST /abort_requests` - Abort in-flight requests without pausing the
  scheduler (send `{}` to abort all, or `{"request_ids": [...]}`)
- `POST /update_weight_version` - Set the `weight_version` label without
  changing weights (send `{"new_version": "v8"}`)
- `GET /weight_info` - Return the latest committed `weight_version`

  Data Parallelism: ~

  When using data parallelism with vLLM's internal load balancer (i.e.
  `data_parallel_backend="ray"`), pause and resume are handled automatically
  across all DP ranks -- a single call is sufficient. When using an external
  load balancer (i.e. multiple independent vLLM instances behind a proxy),
  you must send pause and resume requests to every engine instance
  individually before and after the weight update, and set the weight
  version on every instance too.

TYPICAL ASYNC RL FLOW          *training-async_rl-index-typical-async-rl-flow*

A typical async RL loop with weight syncing looks like this:

1. Start generating rollouts from the current policy
2. Once trainer has new weights to update to, pause generation with
   `mode="keep"`
3. Sync the updated weights from the trainer to the inference engine (see
   |vllm-training-weight_transfer-index|) and set their weight version
4. Resume generation -- in-flight requests continue with the new weights
5. Repeat

The key insight is that requests paused with `mode="keep"` will produce
tokens from the old weights before the pause and tokens from the new weights
after resume. The `clear_cache` parameter controls whether the KV cache is
invalidated during the pause. When `clear_cache=True`, previously cached
key-value entries are discarded, so all tokens generated after resume will
be computed entirely with the new weights. When `clear_cache=False`,
existing KV cache entries are retained, meaning some tokens in context may
still reflect the old weights (stale KV cache).

                          *training-async_rl-index-weight-versions-in-outputs*
WEIGHT VERSIONS IN OUTPUTS

To tell which tokens came from which weights, set a weight-version label
while generation is paused, after the new weights are loaded: pass
`weight_version` to `finish_weight_update`, or call `update_weight_version`
(`POST /update_weight_version` over HTTP). Labels are strings you choose,
such as the trainer step; vLLM doesn't order or check them.

The final output of every sequence then carries `weight_versions`, one span
per label over its output-token indexes. A request paused with `mode="keep"`
across one update gets two spans:

>python
    completion = final_output.outputs[0]
    for span in completion.weight_versions:
        # The tokens in [span.start, span.end) were sampled by weights `span.version`.
        print(span.version, completion.token_ids[span.start : span.end])
<
The offsets cover the whole output, so with streamed delta outputs, collect
the tokens before slicing. `/inference/v1/generate` returns the same list on
each choice; see |online_serving-token_in_token_out-index-weight-versions|.

`/v1/completions` and `/v1/chat/completions` return it on each choice when
the request sets `return_weight_versions: true`. The offsets count the
choice's output tokens, which `return_token_ids` returns as `token_ids`, and
a streamed choice gets the list on its last chunk.

An aborted request returns spans over its partial output. If you resubmit
that output as part of a new prompt, the new request's spans start again at
0, so shift them by the number of tokens already generated before joining
the two lists.

Direct Weight Reload                       *vllm-training-direct_reload-index*

Direct reload updates a running model's weights in place, and is the default
(`VLLM_RELOAD_MODE=auto`) with runtime weight updates
(`--weight-transfer-config`): their weight-transfer updates and disk
`reload_weights` calls reload directly, and each must load every weight.
Anything listed under |training-direct_reload-index-refused-configurations|
reloads layerwise instead (see |vllm-training-layerwise-index|) with a log
saying why. `VLLM_RELOAD_MODE=direct` enables direct reload also without
`--weight-transfer-config` (disk `reload_weights`) and raises an error for
those refusals; `VLLM_RELOAD_MODE=layerwise` turns it off.

HOW IT WORKS                       *training-direct_reload-index-how-it-works*

- Cold start records each tensor's checkpoint layout after loading.
- Begin views every tensor back to its checkpoint layout, in its existing
  storage.
- Load: the model's weight loaders write the new checkpoint tensors, as at
  cold start, through `reload_weights` or a checkpoint-format
  |vllm-training-weight_transfer-index| backend.
- Finish reruns the cold-start post-load processing.

No layer is buffered and no tensor changes address, so captured CUDA graphs
stay valid. Each update must send every weight.

ONLINE QUANTIZATION         *training-direct_reload-index-online-quantization*

With `VLLM_RELOAD_MODE=direct`, the |vllm-quantization-online-index-2|
schemes below quantize each high-precision tensor as it is loaded, into the
layout of the matching pre-quantized checkpoint; the trainer keeps sending
BF16 weights under their checkpoint names.

>bash
    VLLM_RELOAD_MODE=direct vllm serve Qwen/Qwen3-30B-A3B --quantization fp8_per_block
<

--quantization                                       Linear layers  MoE layers
---------------------------------------------------  -------------  ----------
fp8_per_tensor, fp8_per_block, fp8_per_channel,      Supported      Supported
mxfp8
mxfp4 (--quantization-config.moe mxfp4)              Refused        Supported
nvfp4_per_token                                      Stay BF16      Supported

With NVFP4, the w1 and w3 (gate and up) weights of an expert share one
global scale, so both must arrive in the same update (between one
`start_weight_update` and `finish_weight_update`), in either order. The
first of the two is the only tensor direct reload holds: it waits until the
second arrives, and an update that delivers only one of them fails at
finish.

REFUSED CONFIGURATIONS   *training-direct_reload-index-refused-configurations*

- Weight offloading, `torchao` quantization, `draft_lm_head_quantization`,
  and the `sharded_rdt` weight transfer backend.
- LoRA, in `auto` mode only.
- Online quantization. With `VLLM_RELOAD_MODE=direct` the schemes in the
  table above reload directly, except `mxfp4` and `mxfp4_hadamard32` linear
  layers, `int8_per_channel_weight_only`, `lut_b_moe`, a quantized lm_head,
  activation overrides, `hadamard_size`, re-quantization of
  checkpoint-quantized layers, gpt-oss models, and `fp8_per_block` linear
  layers whose tensor-parallel shards are not multiples of 128.
- Layers using Humming kernels.
- Pre-processed weights (weight cache), with a log even under
  `VLLM_RELOAD_MODE=direct`.

The NCCL weight transfer load plan (`use_load_plan`) requires direct reload
and refuses online quantization.

What is Layerwise (Re)loading?                 *vllm-training-layerwise-index*

Layerwise reloading is the system used to handle the loading of new weight
data into existing weight data destinations without triggering recompilation
of the cuda graph and other runtime artifacts. This system is used to enable
QeRL https://arxiv.org/pdf/2510.11696-style post training flows, where
full-precision trainer weights are quantized and loaded into a target vLLM
instance for fast, high-exploration rollouts. The core implementation can be
found in layerwise.py
https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/model_loader/reload/layerwise.py.

                       *training-layerwise-index-layerwise-reloading-for-qerl*
LAYERWISE RELOADING FOR QERL

In order to load new weights into existing weight data destinations, a
weight must undergo the following operations:

- Transfer: weights must be transferred from trainer model to target
  node/device
- Fuse: weight partitions must be fused, for example qkv/gate_up
- Process: this typically means online quantization and kernel-specific
  padding or striding
- Shard: weights must be sharded according to the selected parallelism
  strategy
- Copy: weights must be copied into the existing weight data destinations

Layerwise reloading achieves this using the following steps:

1. Weights are transferred from the trainer to the target (see
   |vllm-training-weight_transfer-index|)
2. Weights loaded via `model.load_weights`, during which they are sharded
   and fused
3. Weights are processed in an online fashion as soon as all of a layer's
   weights are loaded
4. Weights are copied into the existing weight data destinations

For more information on implementation, see
|training-layerwise-index-low-level-layerwise-api|.

         *training-layerwise-index-layerwise-loading-with-online-quantization*
LAYERWISE LOADING WITH ONLINE QUANTIZATION

Online quantization refers to when a user provides full precision weights
and those weights are quantized on-the-fly as they are loaded into the
model. The layerwise reloading system handles this by treating online
quantization as a processing step, which is then handled in an online way
both during first-time load and during reload. A typical online quantization
method implementation should look like this:

>python
    class Fp8PerTensorOnlineLinearMethod(LinearMethodBase):
        """Online version of FP8 per-tensor quantization which loads a full
        precision checkpoint and quantizes weights during loading."""

        uses_meta_device: bool = True

        def create_weights(self, layer: torch.nn.Module, ...):
            # weight is materialized and processed during loading
            layer.weight = ModelWeightParameter(
                data=torch.empty(..., device="meta"),
                weight_loader=weight_loader,
            )

            # set up online processing
            initialize_online_processing(layer)

        def process_weights_after_loading(self, layer: Module) -> None:
            if getattr(layer, "_already_called_process_weights_after_loading", False):
                return

            layer.weight, layer.weight_scale = ops.scaled_fp8_quant(layer.weight)

            # Prevent duplicate processing (e.g., during weight reload)
            layer._already_called_process_weights_after_loading = True
<
With runtime weight updates, |vllm-training-direct_reload-index| is the
default where it applies; layerwise reload serves the configurations it
refuses and `VLLM_RELOAD_MODE=layerwise`.

EXAMPLE USAGES                       *training-layerwise-index-example-usages*

                     *training-layerwise-index-high-level-weight-transfer-api*
High Level Weight Transfer API

The layerwise reloading system is integrated with the post-training weight
transfer system. To use layerwise reloading in conjunction to the weight
transfer system, follow the examples found here
https://github.com/vllm-project/vllm/tree/main/examples/rl.
Checkpoint-format weight transfer engines (e.g. the NCCL and IPC backends)
reload inside their `start_weight_update`/`finish_weight_update` lifecycle,
in the mode `VLLM_RELOAD_MODE` selects: by default
|vllm-training-direct_reload-index| where it applies, else layerwise.

                       *training-layerwise-index-mid-level-reload_weights-api*
Mid Level `reload_weights` API

Layerwise reloading is also exposed via the `reload_weights` API. This
interface can be called using the following code:

>python
    from vllm import LLM

    llm = LLM("Qwen/Qwen3-0.6B")
    llm.collective_rpc("reload_weights")
<
This interface also allows specifying a `weights_path` which can be used to
select a checkpoint path to load from:

>python
    from vllm import LLM

    # fine tuned model checkpoints for testing
    mul_path = "inference-optimization/Qwen3-0.6B-debug-multiply"
    add_path = "inference-optimization/Qwen3-0.6B-debug-add"

    llm = LLM("Qwen/Qwen3-0.6B")
    llm.collective_rpc("reload_weights", kwargs={"weights_path": mul_path})
    llm.generate("3 4 = ")  # 12

    llm.collective_rpc("reload_weights", kwargs={"weights_path": add_path})
    llm.generate("3 4 = ")  # 7
<
Finally, a `weights_iterator` can be provided directly. This iterator can be
lazy or eagerly defined.

>python
    from vllm import LLM

    weights_iterator = [("q_proj", ...), ("k_proj", ...), ...]

    llm = LLM("Qwen/Qwen3-0.6B")
    llm.collective_rpc("reload_weights", kwargs={"weights_iterator": weights_iterator})
<

             *training-layerwise-index-troubleshooting-excessive-memory-usage*
TROUBLESHOOTING EXCESSIVE MEMORY USAGE

Layerwise reload updates DeepSeek-V4.1 CPU-offloaded Engram tables in their
existing host storage. Checkpoint loaders write there directly, and the
|vllm-weight_transfer-sharded_rdt-index| copies received slices straight
into that storage. Post-load hooks run when the update finishes.
GPU-resident and peer-HBM Engram tables use the standard layerwise reload
path.

Layerwise reloading allows users to incrementally load and process weights
as they are loaded into the model. This system relies on buffering layer
weights on device until all weights of a layer have been loaded. However,
without offloading, this approach necessarily causes excessive buffering if
weights are loaded out of order.

For this reason, users must take care as to the order of weights when they
are reloading into the model. Weight should be loaded "in order", meaning
that each layer's weights are fully loaded before beginning to load the next
layer's weights. "Out of order" loading can cause layer weights to stay
buffered while other layer weights are loading, leading to excessive memory
usage. In the example below, q_proj, k_proj, v_proj, and up_proj are all
buffered at the same time, using more memory than if up_proj was loaded
after q_proj, k_proj and v_proj.

Correct Loading                      Incorrect Loading
-----------------------------------  -----------------------------------------

Users will see a warning like the one below if weights are loaded
out-of-order.

>text
    WARNING [layerwise.py:198] Allocating 28.5 MB of device memory to buffers to load ["QKVParallelLinear", "MergedColumnParallelLinear"] layers. This extra memory usage can be avoided by ordering weights by their parent layer when reloading.

                                *vllm-training-prompt_token_id_logprobs-index*
Prompt Token ID Logprobs (Teacher Scoring)

In on-policy distillation, the student records its top-K candidate tokens at
every response position, and the teacher provides the log probabilities of
exactly those candidates as the distillation target. The caller passes one
candidate list per scored row as `prompt_logprob_token_ids`; the teacher
runs a single prefill over the prompt plus response and gathers their log
probabilities on the GPU, starting from `prompt_logprob_start` (typically
the prompt length minus one, so only response positions are scored). The
result is a `[rows, K]` matrix whose row `i` scores prompt token
`prompt_logprob_start + i + 1` and whose columns follow that row's candidate
order, so it lines up position by position with the student's top-K.

QUICK START              *training-prompt_token_id_logprobs-index-quick-start*

>python
    from vllm import LLM, SamplingParams
    from vllm.inputs import TokensPrompt

    llm = LLM(model)
    output = llm.generate(
        TokensPrompt(prompt_token_ids=prompt_ids + response_ids),
        SamplingParams(
            max_tokens=1,
            prompt_logprob_token_ids=student_topk_ids,  # [len(response_ids), K]
            prompt_logprob_start=len(prompt_ids) - 1,
        ),
    )
    scores = output[0].prompt_token_id_logprobs
    # scores.shape == (len(response_ids), K)
    # scores[i, j] = log p(student_topk_ids[i][j] | prompt_ids + response_ids[:i])
<
The same parameters are accepted by the `/inference/v1/generate` HTTP
endpoint (Python and Rust frontends), which returns the matrix as a
base64-encoded `.npy` float32 array:

>python
    import base64, io
    import numpy as np

    scores = np.load(io.BytesIO(base64.b64decode(response["prompt_token_id_logprobs"])))
<
`prompt_logprob_token_ids` is an integer array or a list of lists with
exactly `prompt_len - 1 - prompt_logprob_start` rows; shorter rows are
padded with `-1`, and every `-1` entry scores `-inf`. Pass an `int32` NumPy
array, such as the student's top-K IDs, which is sent to the engine without
conversion; nested lists of Python ints are much slower to copy and
serialize. With a logits `--logprobs-mode`, the matrix holds logits instead
of log probabilities.

REQUIREMENTS            *training-prompt_token_id_logprobs-index-requirements*

- The longest row at most `--max-logprobs` candidates.
- No `--kv-sharing-fast-prefill`.

`prompt_logprob_start` also applies to `prompt_logprobs` (top-K prompt
logprobs): positions up to and including `prompt_logprob_start` get `None`,
and later positions are scored as usual.

Scoring requests skip prefix-cache reads by default. Set
`skip_reading_prefix_cache=False` to reuse locally cached KV for the rows
before `prompt_logprob_start`; every scored row is still computed, and the
hit is block-aligned, so reuse can end a few rows earlier. Without
`prompt_logprob_start`, every row is scored and nothing is reused. KV
connector hits are not used for scoring requests; only the local prefix
cache is reused.

LIMITATIONS              *training-prompt_token_id_logprobs-index-limitations*

- Non-streaming only; `stream=true` requests are rejected.
- Not exposed through the OpenAI-compatible endpoints.

                                          *vllm-training-routed_experts-index*
Routed Experts Return (MoE Routing Replay / R3)

`--enable-return-routed-experts` makes vLLM return the routed experts (the
expert IDs each MoE layer's router selected) for every token of a request.
RL trainers use it for MoE routing replay (R3): the training forward pass
reuses the rollout's routing.

>bash
    vllm serve Qwen/Qwen3-30B-A3B --enable-return-routed-experts
    # offline: LLM("Qwen/Qwen3-30B-A3B", enable_return_routed_experts=True)
<
The flag sets `AuxOutputConfig.enable_return_routed_experts` (full form:
`--aux-output-config '{"enable_return_routed_experts": true, "max_bytes": N}'`).
There is no per-request on/off switch.

REQUIREMENTS                      *training-routed_experts-index-requirements*

Startup fails with a `ValueError` unless:

- the runner is `generate` and the model is MoE;
- prefix caching is enabled (the default). `--no-enable-prefix-caching`
  fails; the old v0.21 advice to disable it is wrong.

Rejected at startup: adaptive speculative verification, PP > 1 and DCP/PCP > 
1. Regular speculative decoding works.

KV connectors are not rejected, including the prefill/decode ones
(`NixlConnector`, `MoRIIOConnector`, `MooncakeConnector`, ...). In a
prefill/decode deployment, however, the decode engine holds no rows for the
KV the prefill engine computed. It accepts that KV only up to
`routed_experts_prompt_start` and computes the rest of the prompt again, so
the output is correct but the prefill work past that position is lost.

                       *training-routed_experts-index-backend-row-restoration*
Backend row restoration

A backend's
|vllm.model_executor.layers.fused_moe.runner.moe_runner.MoERunner| or
`RoutedExpertsCaptureSource` can optionally implement
`restore_routed_experts_rows(topk_ids, ctx) -> Tensor`. During binding, the
capturer selects the first such module in `model.modules()` order and uses
its callback for every captured layer. Without a provider, the existing
DP/TP recovery is used. Existing capture sources need no changes.

The callback must restore this DP rank's token-ordered logical expert IDs
for all captured layers, using the supplied `ForwardContext` rather than the
provider's layer-specific state. It must preserve the input, device, dtype
and top-k width, and keep collective participation consistent across ranks,
including empty ranks. Operations must support graph replay. Models
requiring different per-layer restorers cannot use this hook. Repeated layer
IDs do not select a different restorer; the existing buffer-write semantics
are unchanged.

                   *training-routed_experts-index-routed_experts_prompt_start*
`routed_experts_prompt_start`

Per-request, default `0`: drops the first N prompt-token rows (e.g. routing
already received in earlier turns). Must be `0 <= value <= prompt_len`, else
HTTP 400. Pass it top-level on `/v1/*completions`, inside `sampling_params`
on `/inference/v1/generate`, or as
`SamplingParams(routed_experts_prompt_start=...)`.

ROW STORAGE                        *training-routed_experts-index-row-storage*

The aux output connector (`vllm/distributed/aux_output_connector/`) stores
routing rows per engine, keyed by KV block hash, in the host memory of the
engine's first tensor-parallel worker. Each row exists once, in the engine
that computed it; there is no separate object store to deploy. Every
data-parallel rank is a separate engine with its own rows.

The scheduler holds the rows of every block it keeps in the GPU prefix
cache, and, when a KV connector is configured, of blocks the connector may
load back, up to the store capacity. It reuses a cached block only while it
holds that block's rows and otherwise computes the block again, producing
new rows. Positions before `routed_experts_prompt_start` need no rows: a
request reuses cached KV up to that position even when their rows are gone.

REPLICA AFFINITY              *training-routed_experts-index-replica-affinity*

A later turn of a session reuses its prefix only on the engine that holds
the prefix's KV and rows. Sent to any other engine, the request computes the
whole prefix again:

- time to first token and throughput vary with where each turn lands, and
  multi-turn rollouts pay for their context once per turn;
- the prefix-cache hit rate falls as replicas or load grow and is not
  reproducible across runs;
- a KV store shared between replicas does not fill the gap: the scheduler
  refuses an external KV hit that reaches past `routed_experts_prompt_start`
  unless this engine holds the rows of every loaded block.

Route every request of a session (a multi-turn rollout, or a group of
samples sharing a prompt) to the same engine:

- Put a session ID on each request and have the router map it to an engine
  with consistent hashing (a hash ring or rendezvous hashing), so adding or
  removing an engine remaps only its share of sessions.
- Fall back to another engine only when the target is down or saturated, and
  accept that the next turn of that session recomputes its prefix.
- Set `routed_experts_prompt_start` to the number of tokens whose rows the
  client already holds. A hit then needs rows only for the positions it
  returns, and a shared KV store can serve the earlier turns on another
  engine.

Sessions whose rows are written as objects to a shared Mooncake store,
readable from every replica and released per session, are developed on the
`aux-pr/` branches of the aoshen02/vllm
https://github.com/aoshen02/vllm/tree/aux-pr/7-rename-recomputed-positions
fork. Switch to them when requests of a session cannot be pinned to one
engine or replicas share KV through a store.

               *training-routed_experts-index-weight-updates-and-cache-resets*
WEIGHT UPDATES AND CACHE RESETS

Any reset of the prefix cache drops every row of the engine. That includes
`sleep` at level 1 or 2, `pause_generation(clear_cache=True)` and
`reset_prefix_cache`. A turn sent after the reset has rows only for what it
computes again.

What happens to the KV is your choice, through `reset_connector`:

Call                                  GPU prefix      KV connector     Rows
                                      cache           tier (e.g. CPU
                                                      offload)
------------------------------------  --------------  ---------------  -------
pause_generation(clear_cache=False),  kept            kept             kept
    weights updated in place,
    resume_generation()
    sleep(level=1,                        cleared         kept             cleared
    reset_connector=False)
    sleep(level=1) (default               cleared         cleared          cleared
    reset_connector=True)

- No reset. Updating weights while paused with `clear_cache=False` keeps the
  cache and the rows, so later turns of a session keep their hits. The
  reused KV and rows were computed by the weights in place when each
  position was first computed.
- Sleep, keeping the connector. With `reset_connector=False`, the KV of
  earlier turns can still be loaded back from the connector tier, but its
  rows are gone. Set `routed_experts_prompt_start` to the number of tokens
  whose rows the client already holds: positions before it need no rows, so
  they load from the tier and only the new part of the prompt is computed.
  Without it, the hit reaches past `routed_experts_prompt_start` into blocks
  whose rows this engine no longer holds, so it is refused and the prompt is
  computed again.
- Sleep with the default. Every session computes its whole prefix again on
  the next turn.

Keeping the cache or the connector tier across an update means later turns
reuse KV, and rows, computed by the previous weights. This is a training
decision, not a correctness requirement of vLLM: keep them if your algorithm
accepts that staleness, reset with the defaults if it does not. The defaults
reset because vLLM cannot know which one you want.

SIZING `max_bytes`            *training-routed_experts-index-sizing-max_bytes*

Rows per token take `num_hidden_layers × num_experts_per_tok × itemsize`
bytes, with `itemsize` 1 for at most 256 experts and 2 above; every hidden
layer counts, dense ones included.

- Default (`max_bytes` unset). One block of rows per KV block: the KV cache
  token capacity, logged at startup as `KV cache size: N tokens`, times the
  bytes per token, doubled when a KV connector is configured. The arena is
  anonymous memory, committed as rows are written.
- A smaller `max_bytes` does not save memory. Rows of blocks in the GPU
  prefix cache are never evicted. When they outgrow `max_bytes`, the store
  copies its whole arena into one at least twice as large and logs a
  warning, a latency spike for the steps that wait on the store. The LRU
  drops only rows of blocks the scheduler no longer holds, so the rows of a
  session last as long as its KV does.
- Size the KV cache for the sessions. Later turns hit only while
  `sessions per engine × average context ≤ KV cache token capacity`, with
  headroom for the peaks; past that, KV evicts and turns recompute whatever
  `max_bytes` is.
- Set `max_bytes` only with a KV offload tier larger than the GPU cache. Use
  `(GPU KV tokens + offload tier tokens) × bytes per token × 1.25`, so rows
  stay for every block the tier can load back.

Model                    Bytes per token     Sessions × context per    Rows
                                             engine
-----------------------  ------------------  ------------------------  -------
Qwen3-30B-A3B (48        48 × 8 × 1 = 384 B  32 × 16K = 524K tokens    201 MB
layers, top-8 of 128)
DeepSeek-V4.1-Flash (40  40 × 6 × 2 = 480 B  51 × 200K = 10.2M tokens  4.9 GB
layers, top-6 of 384)
DeepSeek-V4.1-Flash      480 B               51 × 1M = 51M tokens      24.5 GB

For Qwen3-30B-A3B the rows are 0.4% of the bfloat16 KV of the same tokens
(96 KiB per token), so host memory is never the limit; the same holds for
every row of the table on a node with hundreds of GB of host memory. What
limits reuse is the KV cache capacity and replica affinity, not the row
store.

Example: examples/rl/routed_experts_e2e.py
https://github.com/vllm-project/vllm/blob/main/examples/rl/routed_experts_e2e.py.

Sampling Mask (Distribution Replay)        *vllm-training-sampling_mask-index*

When using top-k/top-p sampling for RL rollouts (e.g. GRPO), there is a
systematic mismatch between the truncated distribution the sampler actually
drew from and the full-vocabulary softmax used to compute log-probabilities
during training. The sampling mask feature closes this gap by returning the
exact set of token IDs that survived top-k/top-p/min-p filtering at each
generation step, so the training side can normalize over the same support.

BACKGROUND                           *training-sampling_mask-index-background*

This feature implements the Keep Sampling Mask strategy described in the
DeepSeek-V3.2 technical report
https://huggingface.co/deepseek-ai/DeepSeek-V3.2/blob/main/assets/paper.pdf
(Section 3.3). The key insight: top-k/top-p truncation during rollout
sampling introduces a mismatch between the action spaces of `π_old` and
`π_θ`, which violates the principles of importance sampling and destabilizes
training. By preserving the truncation masks from `π_old` and applying them
to `π_θ` during training, both policies share identical action subspaces.
DeepSeek reports that combining top-p sampling with the Keep Sampling Mask
strategy effectively preserves language consistency during RL training.

QUICK START                         *training-sampling_mask-index-quick-start*

>bash
    vllm serve <model> \
        --return-sampling-mask \
        --logprobs-mode processed_logprobs
<
>python
    from vllm import LLM, SamplingParams

    llm = LLM(model, return_sampling_mask=True,
               logprobs_mode="processed_logprobs")
    output = llm.generate(
        "The capital of France is",
        SamplingParams(temperature=1.0, top_k=50, top_p=0.95, logprobs=1),
    )
    mask = output[0].outputs[0].sampling_mask
    # mask.token_ids: [[187, 326, 512], [42, 88], ...]
    #   mask.token_ids[i] = token IDs in the sampling support for generated token i
<
The mask is also available via the `/inference/v1/generate` HTTP endpoint:

>json
    {
      "choices": [{
        "token_ids": [187, 42, 303],
        "sampling_mask": [[187, 326, 512], [42, 88], [303, 11, 22]],
        "finish_reason": "stop"
      }]
    }
<
With `stream=true`, each chunk carries the masks of the tokens it emits.

REQUIREMENTS                       *training-sampling_mask-index-requirements*

Requirement                         Reason
----------------------------------  ------------------------------------------
--return-sampling-mask              Engine-level opt-in (disables FlashInfer
                                    sampler)
--logprobs-mode processed_logprobs  Returned logprobs are normalized over the
                                    nucleus, not full vocab
temperature > 0                     Greedy has no truncated distribution
top_k > 0                           Bounds mask size; pure top-p can produce
                                    vocab-sized masks

Speculative decoding is supported; each emitted token gets the support of
the target distribution at its position.

The engine rejects unsupported combinations at startup or request time:

- Speculative decoding with adaptive verification
- Diffusion models
- Custom logits processors (engine-level `--logits-processors`)

HOW IT WORKS                       *training-sampling_mask-index-how-it-works*

1. The sampler applies all logit processors (penalties, logit bias, bad
   words, temperature, min-p) and then top-k/top-p filtering, which sets
   excluded logits to `-inf`.
2. After sampling, `torch.isfinite(processed_logits)` identifies the
   surviving token IDs --- this is the sampling mask.
3. The mask is transferred GPU → CPU asynchronously alongside sampled
   tokens.
4. On request completion, per-step masks are merged and converted to
   `list[list[int]]` for the response.

RL TRAINING USAGE             *training-sampling_mask-index-rl-training-usage*

The training side needs two things for the importance ratio `π_θ/π_old`:

`π_old(a|s)` --- old policy's nucleus-normalized logprob: Already returned
by vLLM when `--logprobs-mode processed_logprobs` is set. The `log_softmax`
is computed over processed logits (where filtered tokens are `-inf`), so the
denominator only includes the nucleus.

`π_θ(a|s)` --- current policy's nucleus-normalized logprob: Computed by the
training framework using the mask:

>python
    # mask_ids: list[int], the sampling support for this token
    # logits: the training model's raw logits for this position
    keep = torch.zeros(vocab_size, dtype=torch.bool)
    keep[mask_ids] = True
    masked_logits = logits.masked_fill(~keep, float("-inf"))
    log_prob = log_softmax(masked_logits)[sampled_token_id]
<
Both sides normalize over the same token set, so the importance ratio is
consistent.

            *training-sampling_mask-index-score-centering-with-top-k-logprobs*
SCORE CENTERING WITH TOP-K LOGPROBS

Score centering https://arxiv.org/abs/2609.20807 needs the sampler's top-k
token IDs and logprobs plus the sampled token's logprob; the paper uses
`k=128` and does not need the exact sampling support. vLLM already returns
this through the ordinary `logprobs` parameter:

>bash
    vllm serve <model> --logprobs-mode processed_logprobs --max-logprobs 128
<
>json
    {"sampling_params": {"temperature": 1.0, "top_p": 0.9, "logprobs": 128}}
<
Each position then carries the sampled token's logprob and the top-128
`(token_id, logprob)` pairs, normalized over the post-truncation support:

>json
    {"token": "token_id:11", "logprob": -0.757,
     "top_logprobs": [{"token": "token_id:11", "logprob": -0.757},
                      {"token": "token_id:13", "logprob": -0.632},
                      {"token": "token_id:0",  "logprob": -9999.0}, ...]}
<
- `--max-logprobs` defaults to 20; raise it to the requested `k`.
- Tokens outside the support are returned as `-9999.0` with arbitrary IDs;
  drop them. The finite entries are the sampling mask when it has at most
  `k` tokens.
- The sampled token is always the first entry and may repeat inside the
  top-k.
- The `token_id:<id>` strings come from the OpenAI endpoints with
  `return_tokens_as_token_ids`; `/inference/v1/generate` returns an integer
  `token_id` instead.

LIMITATIONS                         *training-sampling_mask-index-limitations*

- Engine-level flag: `--return-sampling-mask` globally disables the
  FlashInfer fused sampler. All requests pay the cost of the PyTorch
  sampling path, even if they don't need the mask.

Weight Checker                            *vllm-training-weight_checker-index*

The Weight Checker verifies that an RL weight update landed on every rank.
It hashes each model parameter with SHA-256, so a caller can save the
original digests, reset the weights, transfer them back, and confirm they
match.

To also check generated outputs before and after an update, see
|training-weight_transfer-index-verifying-a-new-model-without-a-trainer|.

Enable it with `VLLM_SERVER_DEV_MODE=1`. All operations use
`POST /weight_checker`:

Request                               Response
------------------------------------  ----------------------------------------
{"action": "checksum"}                {"checksums": {key: sha256_hex}}
{"action": "reset"}                   {"status": "reset"}
{"action": "compare", "baseline":     {"match": bool, "mismatches": [key]}
{key: sha256_hex}}

Keys have the form `dp{dp}:pp{pp}:pcp{pcp}:tp{tp}:{tensor_name}`, so each
shard is checked separately. All actions cover the target model's
parameters, which is what weight loading writes; `reset` zeroes them. The
endpoint keeps no state, so the caller holds the baseline. Invalid requests
return HTTP 400.

RL WEIGHT-UPDATE CHECK  *training-weight_checker-index-rl-weight-update-check*

>bash
    URL=http://localhost:8000

    # 1. Stop serving, then save the original digests.
    curl -X POST "$URL/pause?mode=abort"
    curl -X POST $URL/weight_checker -H 'Content-Type: application/json' \
      -d '{"action":"checksum"}' > baseline.json

    # 2. Zero the weights.
    curl -X POST $URL/weight_checker -H 'Content-Type: application/json' \
      -d '{"action":"reset"}'

    # 3. Transfer the original weights with start/update/finish_weight_update.

    # 4. Compare against the baseline; expect {"match": true, "mismatches": []}.
    curl -X POST $URL/weight_checker -H 'Content-Type: application/json' \
      -d "{\"action\":\"compare\",\"baseline\":$(jq .checksums baseline.json)}"

    curl -X POST $URL/resume
<

LIMITATIONS                        *training-weight_checker-index-limitations*

- Stay paused from `checksum` to `compare`: the weights are invalid between
  `reset` and the transfer, and EPLB moves experts while serving.
- A request covers the engines managed by the API server it reaches. With
  several API servers (for example `--data-parallel-external-lb`), send it
  to each one.
- Buffers, draft models and LoRA adapters are not checked.
- CPU backends that repack linear weights hide them from the checker.
- compressed-tensors online transforms are not supported: their Hadamard
  weights are normalized once per storage, so restored copies differ.
- MoE weights padded beyond the checkpoint shape (DeepEP hidden size, MXFP4)
  keep uninitialized padding, so `compare` reports them as mismatches.
- The engine must be awake: sleep levels 1 and 2 release the weight memory.
- `--offload-backend prefetch` is not supported: parameters point at staging
  buffers, not the offloaded weights.
- Hashing copies every weight to CPU, so keep it off latency-sensitive
  paths.

Base Classes and Custom Engines            *vllm-weight_transfer-base-index-2*

The weight transfer system is built from four abstractions, each
independently replaceable:

Abstraction                  Side       Answers
---------------------------  ---------  --------------------------------------
WeightSource                 Trainer    What weights to send
VLLMWeightSyncClient         Trainer    How to reach the inference engine ---
                                        the adapter for your RL stack's own
                                        vLLM wrapper
TrainerWeightTransferEngine  Trainer    How to transmit the bytes
WeightTransferEngine         Inference  How to receive them and load them

The two engines are registered in two separate factories,
|weight_transfer-base-index-2-weighttransfertrainerfactory| and
|weight_transfer-base-index-2-weighttransferenginefactory|. They share
backend names by convention, but a trainer process never instantiates a
worker engine or vice versa, so the registries stay independent.

TRAINER SIDE                       *weight_transfer-base-index-2-trainer-side*

WeightSource                       *weight_transfer-base-index-2-weightsource*

|vllm.distributed.weight_transfer.base.WeightSource| adapts your trainer's
weights to the engines. vLLM ships
|weight_transfer-base-index-2-modulesource| for modules that every rank
holds whole; for anything else (a pipeline stage, a rank's experts, a
Megatron export) you typically write your own. Engines receive HF-format
names, so any gathering, re-fusing or renaming happens in the source.

A source implements `metadata` and one or both iteration modes:

Method        Yields
------------  ----------------------------------------------------------------
metadata      a functools.cached_property: a ParamMeta for every parameter of
              the whole model, identical on every rank; transfers nothing
iter_full()   (name, full tensor) for each name this rank owns
    iter_local()  (name, this rank's piece) for each name this rank owns

NCCL broadcast, IPC and sharded RDT consume `iter_full()`; NCCL M2N consumes
`iter_local()`. Each engine checks at `trainer_init` that the source
implements the mode it needs (`implements_iter_full()` /
`implements_iter_local()`).

                 *weight_transfer-base-index-2-parammeta-ownership-and-layout*
ParamMeta: ownership and layout

>python
    @dataclass(frozen=True)
    class ParamMeta:
        name: str
        dtype: torch.dtype
        shape: tuple[int, ...]                           # full HF shape
        owners: tuple[int, ...] | None = None            # trainer ranks, mesh order; None = all
        mesh_shape: tuple[int, ...] | None = None        # row-major over owners; default (len(owners),)
        placements: tuple[Placement, ...] | None = None  # one per mesh axis; None = replicated
<
- `owners` are global trainer ranks, the `rank` on
  |vllm.distributed.weight_transfer.base.TrainerInitInfo|.
- `placements` are `Replicate()` or `Shard(dim)`, one per mesh axis, and
  describe what `iter_local()` yields.
  |vllm.distributed.weight_transfer.base.Shard| splits the way `torch.chunk`
  does. A source without `iter_local()` leaves them unset.

Because metadata is the same on every rank, every engine plans from it
without exchanging anything. `source.owned_names(rank)` gives the names a
rank iterates. For example, under pipeline parallelism 2 x tensor
parallelism 2 (stage 0 is ranks 0--1, stage 1 is ranks 2--3):

name                                                       owners  placements
---------------------------------------------------------  ------  -----------
model.embed_tokens.weight                                  (0, 1)  (Shard(0),)
model.layers.0.self_attn.o_proj.weight                     (0, 1)  (Shard(1),)
model.layers.27.self_attn.o_proj.weight                    (2, 3)  (Shard(1),)
lm_head.weight                                             (2, 3)  (Shard(0),)

Iteration                             *weight_transfer-base-index-2-iteration*

Both modes yield exactly `owned_names(rank)`, in metadata order, with the
declared dtypes and shapes. Either may run collectives among a parameter's
owners (an FSDP all-gather per tensor or per layer), as long as every owner
iterates in that order. Each call starts a fresh pass.

Keep names that share a layer index (`model.layers.3.*`) contiguous in
`metadata`: sharded RDT transfers |vllm-weight_transfer-sharded_rdt-index|.

ModuleSource                       *weight_transfer-base-index-2-modulesource*

`ModuleSource(model)` covers `module.named_parameters()` when every rank
holds the whole module. A plain tensor is owned by every rank. A `DTensor`
(FSDP2, TP) is owned by its device mesh's ranks, with the mesh's shape and
placements; `iter_full()` yields `full_tensor()` and `iter_local()` yields
`to_local()`. A `DTensor` with other placements (`Partial`, strided shards)
is declared replicated, and `iter_local()` gathers it.

>python
    from vllm.distributed.weight_transfer import ModuleSource

    source = ModuleSource(model)
<

Custom sources                   *weight_transfer-base-index-2-custom-sources*

A source that knows its layout declares it. Here each pipeline stage sends
its own layers:

>python
    from functools import cached_property

    from vllm.distributed.weight_transfer import ParamMeta, WeightSource
    from vllm.distributed.weight_transfer.base import materialize_full_tensor


    class PipelineStageSource(WeightSource):
        """`layout` lists the whole model's (name, dtype, shape, stage) on every
        rank; `stage_ranks[s]` are stage s's trainer ranks; `module` holds this
        rank's stage, with HF names."""

        def __init__(self, module, layout, stage_ranks):
            self._module = module
            self._layout = layout
            self._stage_ranks = stage_ranks

        @cached_property
        def metadata(self):
            return [
                ParamMeta(name, dtype, shape, owners=self._stage_ranks[stage])
                for name, dtype, shape, stage in self._layout
            ]

        def iter_full(self):
            params = dict(self._module.named_parameters())
            for meta in self.metadata:
                if meta.name in params:
                    yield meta.name, materialize_full_tensor(params[meta.name])
<
Each engine's page says which ownership layouts it can send.

VLLMWeightSyncClient       *weight_transfer-base-index-2-vllmweightsyncclient*

This is the adapter for however your RL stack reaches vLLM. Many RL
frameworks wrap inference engines in their own abstractions, and each
reaches vLLM its own way.
|vllm.distributed.weight_transfer.base.VLLMWeightSyncClient| is the single
seam where that bespoke shape is adapted, so weight sync engines remain
control plane agnostic.

The contract is only this: however the wrapper is shaped, it must bottom out
in the same four calls --- `init_weight_transfer_engine` once at setup, then
`start_weight_update` → one or more `update_weights` →
`finish_weight_update` per round. Everything a trainer engine needs from the
inference side goes through them.

>python
    class VLLMWeightSyncClient(Protocol):
        def init_weight_transfer_engine(self, init_info: dict[str, Any]) -> None: ...
        def start_weight_update(self) -> None: ...
        def update_weights(self, update_info: dict[str, Any]) -> None: ...
        def finish_weight_update(self, weight_version: str | None = None) -> None: ...
<
It is a `@runtime_checkable` structural `Protocol` (PEP 544), which is what
makes adapting cheap: any object with those four methods already satisfies
it. An existing wrapper in your framework can usually become a client by
gaining four forwarding methods.

Two implementations ship with vLLM:

Client                              Talks to
----------------------------------  ------------------------------------------
RayVLLMWeightSyncClient(handle)     One or more AsyncLLM/LLM Ray actors.
                                    Accepts a list and fans each call out to
                                    every handle, blocking on all of them, so
                                    a multi-actor (e.g. multi-DP) deployment
                                    is driven as one unit
HTTPVLLMWeightSyncClient(base_url,  A vLLM server over the RLHF HTTP routes
    timeout=300)

Custom weight sync clients can be implemented like so:

>python
    class MyFrameworkWeightSyncClient:
        """Adapts one RL framework's rollout pool to the four weight-sync calls."""

        def __init__(self, rollout_pool):
            self.pool = rollout_pool          # whatever your stack already has

        def init_weight_transfer_engine(self, init_info):
            # Fan out to every replica and block: all of them receive weights.
            self.pool.broadcast_rpc("init_weight_transfer_engine", init_info=init_info)

        def start_weight_update(self):
            self.pool.broadcast_rpc("start_weight_update")

        def update_weights(self, update_info):
            self.pool.broadcast_rpc("update_weights", update_info=update_info)

        def finish_weight_update(self, weight_version=None):
            self.pool.broadcast_rpc("finish_weight_update")
            if weight_version is not None:
                self.pool.broadcast_rpc("update_weight_version", weight_version)
<
Two things to get right in any adapter:

- Reach every replica, and block until all of them are done. A weight update
  is not a load-balanced request: every worker holding a copy of the model
  must receive it. Returning before they all finish lets the trainer race
  ahead of workers still loading. (Both built-in clients do this --- Ray by
  fanning out over its handles, HTTP because the server's DP client
  broadcasts internally.)
- Raise on failure. Trainer engines rely on exceptions to surface
  inference-side errors; a client that swallows them turns a failed sync
  into silently stale weights, or into a hang for backends whose transfer
  rendezvouses with the worker.

  Note: ~

  HTTP cannot carry raw CUDA IPC handles, so
  |vllm.distributed.weight_transfer.clients.HTTPVLLMWeightSyncClient|
  pickles and base64-encodes them into an `ipc_handles_pickled` field. The
  worker deserializes it only when `VLLM_ALLOW_INSECURE_SERIALIZATION=1`.
  Backends whose payloads are JSON-native (NCCL) pass through untouched.

                    *weight_transfer-base-index-2-trainerweighttransferengine*
TrainerWeightTransferEngine

The trainer-side engine: it holds the transport state (NCCL communicators,
IPC device info, transfer plans), pulls weights from a
|vllm.distributed.weight_transfer.base.WeightSource|, and drives the
inference side through a
|vllm.distributed.weight_transfer.base.VLLMWeightSyncClient|. It is generic
over its init info type, constructed by the `trainer_init` classmethod
factory, and driven by `send_weights()`.

Method                              Description
----------------------------------  ------------------------------------------
trainer_init(init_info, *, client,  Classmethod. Rendezvous with the inference
    source=None)                        side and return a ready instance
    send_weights()                      Push weights and drive the full update
                                    round trip
shutdown()                          Tear down communicators / process groups.
                                    Default no-op

Both `trainer_init` and `send_weights` are called on every trainer rank.
`is_sender` is resolved once, at `trainer_init`, from `init_info.rank`. Each
engine holds the real client on every rank but guards the control-plane RPCs
and the transmit on `self.is_sender`, so only the sender touches the wire;
non-sender ranks still run every collective so the group stays aligned.

The trainer side takes no
|vllm.config.weight_transfer.WeightTransferConfig|. The backend comes from
the init info's `backend` `ClassVar`, and the wire params ride the init info
too.

TrainerInitInfo                 *weight_transfer-base-index-2-trainerinitinfo*

The `init_info` passed to `trainer_init` above. It is how a caller
configures a transfer: it selects the backend, says which rank this process
is, and carries the wire params. Each backend subclasses it; the base class
holds the one field every backend needs.

>python
    @dataclass
    class TrainerInitInfo:
        backend: ClassVar[str]        # factory dispatch key
        rank: int = field(kw_only=True)

        @property
        def is_sender(self) -> bool:
            return self.rank == 0
<
- `rank` is this trainer process's rank, supplied explicitly. The engine
  does not read it from a global process group, which is ambiguous once
  several groups (FSDP / TP / PP / EP) exist. Rank 0 is always the sender
  --- this is what `trainer_init` resolves into `is_sender`. It is
  keyword-only, so backend subclasses can add positional fields freely.
- `backend` is a `ClassVar`, not an `__init__` field: it is a fixed
  per-backend constant that the factory reads to dispatch, which is why
  callers never pass a `backend=` argument. Every subclass must set it ---
  `__init_subclass__` raises otherwise.

Subclasses also carry the transfer's wire params (`packed`, buffer sizes).
The sender propagates them to the worker inside `trainer_init`, so the two
sides cannot disagree. See |weight_transfer-nccl-index-nccltrainerinitinfo|
and |weight_transfer-ipc-index-ipctrainerinitinfo| for the concrete fields.

                  *weight_transfer-base-index-2-full-resync-vs-delta-backends*
Full-Resync vs. Delta Backends

`source` is optional, which splits the backends into two shapes:

- Full resync (NCCL, IPC) --- a stable
  |vllm.distributed.weight_transfer.base.WeightSource| is fixed at
  `trainer_init` and re-iterated each round; `send_weights()` takes no
  arguments. These backends validate that `source` is non-null themselves.
- Delta (sparse NCCL) --- the payload differs every round, so there is no
  stable source. The engine takes no `source` and each round's payload is
  passed straight to `send_weights(patches)`.

           *weight_transfer-base-index-2-implementing-a-custom-trainer-engine*
Implementing a Custom Trainer Engine

>python
    from dataclasses import dataclass
    from typing import ClassVar

    from typing_extensions import Self

    from vllm.distributed.weight_transfer.base import (
        TrainerInitInfo,
        TrainerWeightTransferEngine,
        VLLMWeightSyncClient,
        WeightSource,
    )


    @dataclass
    class MyTrainerInitInfo(TrainerInitInfo):
        backend: ClassVar[str] = "my_backend"

        endpoint: str
        chunk_size_bytes: int = 256 * 1024 * 1024   # a wire param: shipped to the worker


    class MyTrainerWeightTransferEngine(TrainerWeightTransferEngine[MyTrainerInitInfo]):
        init_info_cls = MyTrainerInitInfo

        def __init__(self, *, client, source, is_sender=True, chunk_size_bytes=0):
            super().__init__(client=client, source=source, is_sender=is_sender)
            self.chunk_size_bytes = chunk_size_bytes

        @classmethod
        def trainer_init(
            cls,
            init_info: MyTrainerInitInfo,
            *,
            client: VLLMWeightSyncClient,
            source: WeightSource | None = None,
        ) -> Self:
            if source is None:
                raise ValueError("my_backend requires a WeightSource.")
            engine = cls(
                client=client,
                source=source,
                is_sender=init_info.is_sender,
                chunk_size_bytes=init_info.chunk_size_bytes,
            )
            if engine.is_sender:
                # Ship the must-agree wire params so the worker decodes exactly as
                # this trainer encodes, then open the trainer-side endpoint.
                engine.client.init_weight_transfer_engine(
                    {"chunk_size_bytes": init_info.chunk_size_bytes}
                )
            return engine

        def send_weights(self) -> None:
            assert self.source is not None
            meta = self.source.metadata
            if not self.is_sender:
                for _ in self.source.iter_full():  # join the source's collectives
                    pass
                return

            self.client.start_weight_update()
            self.client.update_weights(
                {
                    "names": [m.name for m in meta],
                    "dtype_names": [str(m.dtype).split(".")[-1] for m in meta],
                    "shapes": [list(m.shape) for m in meta],
                }
            )
            for name, tensor in self.source.iter_full():
                ...                            # transmit
            self.client.finish_weight_update()
<
Two things to get right, both of which have bitten the built-in backends:

- Drain before returning. `send_weights` must not return with transfers
  still in flight. Anything keeping a send buffer alive dies with the frame,
  and the inference side's `finish_weight_update` post-processing can
  otherwise finalize weights that have not landed.
- Never join a control-plane thread on the error path. If you run
  `update_weights` on a side thread concurrently with a transmit (as NCCL
  does) and the transmit raises, the worker is still blocked in the matching
  collective and will never return. Shut the executor down without waiting,
  so the real exception surfaces instead of hanging.

INFERENCE SIDE                   *weight_transfer-base-index-2-inference-side*

WeightTransferEngine       *weight_transfer-base-index-2-weighttransferengine*

A generic abstract class parameterized by two dataclass types:

- `TInitInfo` (extends
  |vllm.distributed.weight_transfer.base.WeightTransferInitInfo|):
  backend-specific initialization parameters.
- `TUpdateInfo` (extends
  |vllm.distributed.weight_transfer.base.WeightTransferUpdateInfo|):
  backend-specific weight update metadata.

Subclasses must implement five methods:

Method                           Description
-------------------------------  ---------------------------------------------
init_transfer_engine(init_info)  Initialize the communication channel on each
                                 inference worker, and record the
                                 trainer-supplied wire params
start_weight_update()            Prepare for an update (e.g. begin layerwise
                                 reload); no-op for in-place engines
finish_weight_update()           Finalize the update (e.g. finalize layerwise
                                 reload); no-op for in-place engines
receive_weights(update_info)     Receive weights and load them into self.model
    shutdown()                       Clean up resources

The base class provides:

1. `__init__`, taking `config`
   (|vllm.config.weight_transfer.WeightTransferConfig|), `vllm_config`
   (|vllm.config.vllm.VllmConfig|), `device` (`torch.device`), and `model`
   (`nn.Module`).
2. `update_weights(update_info_dict)`, a thin wrapper for `receive_weights`:
   it parses the dict into the typed dataclass, calls `receive_weights`, and
   synchronizes the device --- unless the engine sets `defers_processing`,
   below.
3. `parse_init_info` / `parse_update_info`, which convert API-level dicts
   into the typed dataclasses and raise `ValueError` on a bad payload.
4. `set_weight_update_target` / `reset_weight_update_target`, used to
   retarget an update at the speculative draft model.

  Read wire params from the handshake, not the payload: ~

  Anything the two sides must agree on --- `packed`, buffer geometry ---
  arrives on the init info and should be stored on `self` in
  `init_transfer_engine`, then read from `self` in `receive_weights`.
  Per-round update info carries only per-round metadata. This is what makes
  a trainer/worker mismatch unrepresentable.

  defers_processing: when a returned update means queued, not applied: ~

  An engine that pipelines its GPU post-processing onto background threads
  cannot let `update_weights` synchronize the device --- that would block on
  those threads and serialize the pipeline. Such an engine sets the class
  attribute `defers_processing = True`, omits the per-update sync, and
  guarantees completion in `finish_weight_update` instead.

  Callers that go through `finish_weight_update` need do nothing; the engine
  drains there. A caller that drives the tail itself --- running its own
  `finalize_layerwise_reload`, say --- must check the flag and call
  `drain_pending()` first, because with it set a returned `update_weights`
  means queued, not applied. `drain_pending()` is idempotent, and a no-op on
  an engine that processes synchronously, so it is always safe to call.

  |vllm-weight_transfer-sharded_rdt-index| is the built-in engine that sets
  it: it scatters and quantizes on background threads with their own CUDA
  streams, so its `drain_pending()` joins both queues and syncs both streams
  before `finalize_layerwise_reload` runs.

----------------------------------------------------------------------------
Weight Transfer                          *vllm-training-weight_transfer-index*

vLLM provides a pluggable weight transfer system for synchronizing model
weights from a training process to the inference engine during reinforcement
learning (RL) workflows. This is essential for RLHF, GRPO, and other online
RL methods where the policy model is iteratively updated during training and
the updated weights must be reflected in the inference engine for rollout
generation.

ARCHITECTURE                     *training-weight_transfer-index-architecture*

Weight transfer has two engines, one per process, and they are symmetric:

           Trainer process                       Inference workers
---------  ------------------------------------  -----------------------------
Class      TrainerWeightTransferEngine           WeightTransferEngine
Built by   WeightTransferTrainerFactory.trainer_init(...)  vLLM, from
                                                 WeightTransferConfig
Driven by  send_weights()                        the four-phase protocol below
Holds      communicators, transfer plans, wire   communicators, the target
           params                                model

The trainer engine is stateful: it owns its communicators and wire params,
pulls weights from a |weight_transfer-base-index-2-weightsource|, and drives
the inference side through a
|weight_transfer-base-index-2-vllmweightsyncclient|. Trainer code never has
to know the transport, and never has to thread transfer state back in on
every round --- one `send_weights()` call per sync.

Under the hood every round is the same four-phase protocol, which the
trainer engine drives on your behalf:

1. Initialization (`init_weight_transfer_engine`): establishes the
   communication channel between the trainer and inference workers. Called
   once, from `trainer_init`, before the training loop begins.
2. Start (`start_weight_update`): prepares the inference engine for a weight
   update.
3. Weight Update (`update_weights`): transfers updated weights. May be
   called one or more times (e.g. for chunked transfers).
4. Finish (`finish_weight_update`): finalizes the update (e.g. runs
   post-processing for checkpoint-format weights). Called once after all
   weights have been transferred.

Checkpoint-format backends reload in the mode set by the `VLLM_RELOAD_MODE`
environment variable: by default |vllm-training-direct_reload-index| where
it applies, else |vllm-training-layerwise-index|.

AVAILABLE BACKENDS         *training-weight_transfer-index-available-backends*

Backend       Transport                        Use Case
------------  -------------------------------  -------------------------------
NCCL          NCCL broadcast                   Separate GPUs for training and
                                               inference
IPC           CUDA IPC handles                 Colocated training and
                                               inference on same GPU
sparse_nccl   NCCL broadcast                   Checkpoint-coordinate sparse
                                               weight patches
sharded_rdt   NIXL / Ray Direct Transport      Very large models where each
              (pull-based)                     worker needs only its own slice
                                               (MoE with expert parallelism)
nccl_m2n      NCCL M2N reshard                 Trainer and inference use
                                               different sharding layouts
ModelExpress  ModelExpress version-based       Install immutable published
              transfer                         weight versions, including
                                               object-storage checkpoints and
                                               deltas

Trainer Side                     *training-weight_transfer-index-trainer-side*

Build the engine once, then call `send_weights()` once per sync:

>python
    from vllm.distributed.weight_transfer import (
        ModuleSource,
        HTTPVLLMWeightSyncClient,
        WeightTransferTrainerFactory,
    )
    from vllm.distributed.weight_transfer.nccl_engine import NCCLTrainerInitInfo

`send_weights()` drives start → update → finish on the inference side and
the data-plane transfer, including any concurrency the backend needs (NCCL,
for example, must run the workers' `update_weights` at the same time as the
trainer's broadcast, since both rendezvous inside the same NCCL calls).

There is no `backend=` argument on the trainer side: each
|vllm.distributed.weight_transfer.base.TrainerInitInfo| subclass declares
its own `backend`, and the factory dispatches on it.

MULTI-RANK TRAINERS       *training-weight_transfer-index-multi-rank-trainers*

For sharded trainers (FSDP, TP/PP/EP), every trainer rank builds an engine
and calls `send_weights()`. Rank 0 is the sender: only it holds a
communicator, talks to the client, and puts bytes on the wire. Non-sender
ranks still iterate the |vllm.distributed.weight_transfer.base.WeightSource|
over the parameters they own, because materializing a parameter is usually
itself a collective among its owners (an FSDP `full_tensor()` all-gather, a
Megatron export) that would deadlock if some of them skipped it. Which ranks
own which parameter is declared in
|weight_transfer-base-index-2-parammeta-ownership-and-layout|. Only
|vllm-weight_transfer-sharded_rdt-index| and
|weight_transfer-nccl-index-broadcasting-ranks| accept ranks that own
different parameters, such as pipeline stages. Pipeline-parallel support for
IPC is in progress; until then it, like NCCL M2N, needs every parameter
owned by rank 0 or by every rank (see each backend's Limitations).

Pass each process's own `rank` on the init info. It is explicit rather than
read from a global process group, which is ambiguous once several groups
(FSDP / TP / PP / EP) exist.

>python
    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=NCCLTrainerInitInfo(..., rank=torch.distributed.get_rank()),
        client=client,
        source=ModuleSource(model),
    )
    engine.send_weights()  # called on every rank

API ENDPOINTS                   *training-weight_transfer-index-api-endpoints*

When running vLLM as an HTTP server, the following endpoints are available
for weight transfer.
|vllm.distributed.weight_transfer.clients.HTTPVLLMWeightSyncClient| speaks
the first five for you. A trainer may also implement the protocol directly
without importing vLLM: see the wire contracts in
|weight_transfer-nccl-index-trainer-without-vllm-over-http| and
|weight_transfer-ipc-index-trainer-without-vllm-over-http|. This keeps the
trainer decoupled from vLLM: it needs no vLLM install or version pin, only
this documented HTTP and wire contract, so trainer and server can upgrade
independently (non-PyTorch trainers such as JAX can use it too).

Endpoint                          Method  Description
--------------------------------  ------  ------------------------------------
/init_weight_transfer_engine      POST    Initialize the weight transfer
                                          engine with backend-specific info
/start_weight_update              POST    Start a weight update
/update_weights                   POST    Transfer a batch of weights with
                                          backend-specific metadata
/finish_weight_update             POST    Finish the update and optionally
                                          commit its weight_version
/shutdown_weight_transfer_engine  POST    Release the transfer channel without
                                          stopping inference
/update_weight_version            POST    Update weight_version without
                                          changing model weights
/weight_info                      GET     Get the latest committed weight
                                          version
/pause                            POST    Pause generation before weight sync
                                          to handle inflight requests
/resume                           POST    Resume generation after weight sync
/get_world_size                   GET     Get the number of inference workers
                                          (useful for NCCL world size
                                          calculation)

  Note: ~

  The HTTP weight transfer endpoints require `VLLM_SERVER_DEV_MODE=1` to be
  set.

  Warning: ~

  If `/update_weights` fails, the model is left mid-reload while `/health`
  stays 200, and `/finish_weight_update` is rejected. Before generating
  again, resend a full `/start_weight_update` → `/update_weights` →
  `/finish_weight_update` (see #57854
  https://github.com/vllm-project/vllm/pull/57854).

The Rust frontend's optional gRPC `Control` service exposes the same pause,
sleep, weight-transfer, and weight-version lifecycle for trusted sidecars.
The `ServerInfo.rl_capabilities` response reports whether weight transfer
and sleep mode were configured. Backend-specific `init_info` and
`update_info` remain JSON metadata; model tensors continue to move over the
configured NCCL, IPC, sparse-NCCL, or sharded-RDT transport.

EXTENDING THE SYSTEM     *training-weight_transfer-index-extending-the-system*

Every piece of the system is replaceable: the weights you send
(|vllm.distributed.weight_transfer.base.WeightSource|), the control-plane
transport (|vllm.distributed.weight_transfer.base.VLLMWeightSyncClient|),
and the transports themselves (both engine ABCs, each with its own factory
registry). See |vllm-weight_transfer-base-index-2|.

----------------------------------------------------------------------------
IPC Engine                                    *vllm-weight_transfer-ipc-index*

The IPC weight transfer engine uses CUDA IPC (Inter-Process Communication)
handles to share GPU memory directly between the trainer and inference
workers on the same GPU. This avoids any data copying, making it the most
efficient option when colocating training and inference. Multi-GPU setups
are supported --- weights are all gathered by each GPU and are extracted by
the correct colocated process.

WHEN TO USE IPC                    *weight_transfer-ipc-index-when-to-use-ipc*

- Training and inference share the same GPU(s) (colocated)

HOW IT WORKS                          *weight_transfer-ipc-index-how-it-works*

1. The trainer creates CUDA tensors for each weight and generates IPC
   handles using `torch.multiprocessing.reductions.reduce_tensor`. In
   multi-GPU setups (e.g. FSDP), each trainer rank materializes the full
   tensor for each parameter onto its own GPU before generating the handle
   --- which |vllm.distributed.weight_transfer.base.ModuleSource| does for
   you. Each rank serves its colocated worker, so every rank must own every
   parameter; a partitioned source is rejected.
2. Every trainer rank contributes its handles to an all-gather; the sender
   merges them so each payload maps every GPU UUID to its args, and ships
   the merged handles to the inference engine through the client. Each
   worker reads only the handle for its own GPU.
3. The inference worker reconstructs the tensors from the handles using
   `rebuild_cuda_tensor`, reading directly from the trainer's GPU memory.

Unlike NCCL, IPC transfer is straight-line: `update_weights` is the
transfer, and it rides the client, so there is no concurrent broadcast to
overlap with.

  Note: ~

  The handle all-gather in step 2 runs over the default process group, so it
  assumes that group is exactly the set of colocated trainer ranks and that
  the sender is a member. It is a no-op when no distributed group exists.

  Warning: ~

  IPC handles involve sending serialized Python objects. When using HTTP
  transport, you must set `VLLM_ALLOW_INSECURE_SERIALIZATION=1` on both the
  server and client. This is because IPC handles are pickled and
  base64-encoded for HTTP transmission.

INFERENCE SIDE                      *weight_transfer-ipc-index-inference-side*

>python
    from vllm import LLM
    from vllm.config import WeightTransferConfig

    llm = LLM(model="my-model", weight_transfer_config=WeightTransferConfig(backend="ipc"))
<
>bash
    vllm serve my-model --weight-transfer-config '{"backend": "ipc"}'
<
IPC needs no data-plane rendezvous, so `init_transfer_engine` opens no
channel --- it only records the `packed` flag the trainer ships at the
handshake, which `receive_weights` then reads. Whether a transfer is packed
is therefore never something you configure on the inference side.

TRAINER SIDE                          *weight_transfer-ipc-index-trainer-side*

>python
    from vllm.distributed.weight_transfer import (
        ModuleSource,
        HTTPVLLMWeightSyncClient,
        WeightTransferTrainerFactory,
    )
    from vllm.distributed.weight_transfer.ipc_engine import IPCTrainerInitInfo

    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=IPCTrainerInitInfo(rank=0, packed=False),   # rank 0 is the sender
        client=HTTPVLLMWeightSyncClient("http://localhost:8000"),
        source=ModuleSource(model),
    )

    engine.send_weights()   # once per sync
<
`send_weights()` drives `start_weight_update`, the transfer itself, and
`finish_weight_update`, and holds strong references to the IPC-shared copies
until after the post-send barrier --- the consumer's views would otherwise
dangle.

Any |weight_transfer-base-index-2-vllmweightsyncclient| works here --- the
built-in HTTP and Ray clients, or an adapter for your own stack. The engine
is identical either way.

IPCTrainerInitInfo              *weight_transfer-ipc-index-ipctrainerinitinfo*

Field                     Default  Description
------------------------  -------  -------------------------------------------
rank                      ---        Keyword-only. This trainer process's rank;
                                   0 is the sender
packed                    False    Chunked, bounded-memory transfer (see
                                   below)
packed_buffer_size_bytes  1 GiB    Chunk size when packed=True, rounded down
                                   to a multiple of 16

`packed` is a must-agree wire param: `trainer_init` ships it to the worker,
which records it and decodes accordingly. It is not a
|vllm.config.weight_transfer.WeightTransferConfig| field and not a per-round
`update_weights` field. `packed_buffer_size_bytes` is producer-only --- the
producer sends the chunk size with the first chunk.

PACKED (CHUNKED) TRANSFER  *weight_transfer-ipc-index-packed-chunked-transfer*

By default, all weights are sent in a single `update_weights` call. For
large models, this requires the full model to reside in GPU memory on both
sides simultaneously. Setting `packed=True` enables chunked transfer with
bounded GPU memory:

- Weights are laid out as one byte stream, each starting 16-byte aligned,
  and cut into chunks of `packed_buffer_size_bytes`; a tensor larger than a
  chunk is split across chunks (the same layout as NCCL packed transfer).
- Each chunk is sent as a separate `update_weights` call within a single
  `start_weight_update` / `finish_weight_update` bracket, so the model is
  prepared for reloading once at the start and finalized once at the end
  regardless of chunk count.
- One buffer on the engine's CUDA device, reused for every chunk of a
  transfer, bounds its extra GPU memory: up to `packed_buffer_size_bytes`,
  smaller for a transfer that fits in one chunk (it starts at 64 MiB, or the
  first chunk's bytes if larger, and doubles as needed; while growing, the
  old buffer is briefly held too and may stay reserved by PyTorch's caching
  allocator). CPU-resident sources work too but are copied synchronously,
  which is slower. A non-contiguous tensor split across chunks also needs a
  contiguous copy of its full size on the trainer while it is sent.

>python
    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=IPCTrainerInitInfo(
            rank=0,
            packed=True,
            packed_buffer_size_bytes=256 * 1024 * 1024,  # 256 MB chunks
        ),
        client=client,
        source=ModuleSource(model),
    )
<
On a multi-rank trainer the producer reuses one buffer across chunks, so
packed mode carries a per-chunk barrier across ranks: without it, a rank
could overwrite its buffer while its colocated worker is still reading the
current chunk. This is handled inside `send_weights()`.

                    *weight_transfer-ipc-index-trainer-without-vllm-over-http*
TRAINER WITHOUT VLLM OVER HTTP

A colocated trainer can speak the
|training-weight_transfer-index-api-endpoints| directly, with only PyTorch
and an HTTP client. The server needs `VLLM_ALLOW_INSECURE_SERIALIZATION=1`;
without it, init and start return 200 and the first `/update_weights`
returns 500. Reference: `rlhf_http_ipc_no_vllm.py`
https://github.com/vllm-project/vllm/blob/main/examples/rl/rlhf_http_ipc_no_vllm.py.

`POST /init_weight_transfer_engine` body:
`{"init_info": {"packed": false}}`.

`POST /update_weights` body `{"update_info": {...}}`:

Field                       Meaning
--------------------------  --------------------------------------------------
names, dtype_names, shapes  Checkpoint names, torch dtype attribute names
                            ("bfloat16"), full shapes. Packed: only the
                            tensors whose first bytes are in this chunk
ipc_handles_pickled         base64(pickle.dumps(handles)). Unpacked: a list
                            with one dict per name. Packed: one dict for the
                            shared buffer in the first chunk, {} in the rest
chunk_capacity              Packed: the chunk size in bytes, a multiple of 16,
                            on the first chunk only
last                        Packed: true on the chunk that ends the transfer,
                            else false (the default)

- A handle dict is `{gpu_uuid: reduce_tensor(t)[1]}` with one entry per GPU
  the server uses (`torch.multiprocessing.reductions.reduce_tensor`).
  `gpu_uuid = str(torch.cuda.get_device_properties(i).uuid)`, without the
  `GPU-` prefix that `nvidia-smi` prints. The worker overwrites `args[6]`
  (device index) with its own.
- `ipc_handles` (unpickled) is not JSON-serializable; over HTTP use
  `ipc_handles_pickled`.
- Packed: export one `uint8` buffer once per transfer, large enough for its
  largest chunk; send its handle and `chunk_capacity` with the first chunk
  only, and reuse it for every chunk. Lay the tensors'
  `t.contiguous().view(-1).view(torch.uint8)` bytes out as one stream, each
  tensor starting at a multiple of 16, and send a chunk each time the buffer
  is full (or only alignment padding would fit), then the rest; a tensor
  crossing a cut continues at offset 0 of the next chunk. Mark the last
  chunk `last`: `/finish_weight_update` fails if a transfer did not reach
  it; a new full update repairs the model. Synchronize before each
  `/update_weights`; do not overwrite the buffer until the call returns.
- Keep every exported tensor alive until `/finish_weight_update` returns,
  then drop the references and call `torch.cuda.ipc_collect()`.
- Multi-rank trainers: each rank exports handles for its own GPU, the ranks
  gather the `{uuid: args}` dicts to rank 0 over their own
  `torch.distributed` group and merge them per index, and rank 0 sends all
  HTTP. In packed mode, barrier before and after each `/update_weights`.

RANK-LOCAL UPDATES              *weight_transfer-ipc-index-rank-local-updates*

For different parameter subsets per worker, `update_info` may be a list
indexed by worker rank. This form is IPC-only because collective backends
require every worker to participate.

LIMITATIONS                            *weight_transfer-ipc-index-limitations*

- Colocated only. Each trainer rank shares memory with the inference worker
  on its own GPU; trainer and inference on separate GPUs need another
  backend.
- Pipeline-parallel trainers are not supported yet (work in progress). Every
  trainer rank serves its colocated worker the whole model, so every rank
  must own every parameter. A source whose ranks own different parameters
  (pipeline stages, or experts held by only some ranks) is rejected at
  `trainer_init`.
- A full copy per GPU. Each rank materializes every parameter in full on its
  GPU. Unpacked, the whole model stays resident until the round finishes;
  set `packed=True` to bound it to one chunk.
- The handle all-gather runs over the default process group, which must be
  exactly the colocated trainer ranks.

NCCL M2N Engine                               *vllm-weight_transfer-m2n-index*

The `nccl_m2n` weight transfer engine uses NCCL M2N
https://github.com/NVIDIA/nccl-extensions to reshard weights between two
disjoint meshes of GPUs --- the trainer and the inference workers --- in a
single collective per parameter. Unlike the broadcast-based
|vllm-weight_transfer-nccl-index|, the trainer sends its local shard as-is:
no full tensor is ever materialized on the training side, whatever its
parallelism layout.

WHEN TO USE NCCL M2N          *weight_transfer-m2n-index-when-to-use-nccl-m2n*

- The trainer and the inference engine use different parallelism layouts
  (e.g. trainer FSDP/EP, inference TP) and gathering full tensors on the
  trainer is expensive
- Training and inference are on separate GPUs, possibly across nodes
- You want weight sync off the critical path of an async RL loop

REQUIREMENTS                          *weight_transfer-m2n-index-requirements*

This backend depends on the `nccl-extensions` Python package (and its
`nccl4py` dependency), which vLLM does not install. Install both against a
compatible NCCL 2.30.5 or newer runtime. The backend creates its data-plane
communicator through `nccl4py` and passes that communicator directly to
`nccl.m2n`.

The backend imports the runtime lazily, so vLLM is unaffected unless you
select it.

HOW IT WORKS                          *weight_transfer-m2n-index-how-it-works*

1. A |vllm.distributed.utils.StatelessProcessGroup| exchanges metadata and
   the NCCL unique ID. The trainer ranks and all inference workers then
   create one `nccl.core.Communicator`: trainer ranks occupy `[0, T)` and
   workers `[T, T + N)`. The communicator is passed directly to each M2N
   collective.
2. At the init handshake the trainer ships the full transfer plan: the
   session-wide destination mesh, then each parameter's name, dtype, shape,
   source mesh, and source placements. The workers resolve the matching
   destination placements and publish them over the data-plane communicator;
   the meshes themselves are declared, not negotiated.
3. Each round, both sides issue one `reshard` per parameter in the same
   order. Every rank in the communicator participates in every reshard, so
   --- as with the NCCL engine --- the worker must be inside
   `update_weights` while the trainer sends. The trainer engine handles that
   concurrency itself.

Destination resolution      *weight_transfer-m2n-index-destination-resolution*

A parameter is resharded directly into the live vLLM parameter when its
checkpoint name maps 1:1 onto a model parameter whose shape is either
identical to the checkpoint shape (replicated) or differs on exactly one dim
by the tensor-parallel factor. That rank then only ever receives its own
shard.

Anything else falls back to receiving the full tensor and letting
`load_weights` do the sharding, exactly as the NCCL engine does for every
parameter. The fallback covers:

- fused parameters (`qkv_proj`, `gate_up_proj`, MoE `w13`/`w2`), whose
  checkpoint names do not name a model parameter
- quantized models, where the weight loader does more than a sharded copy
- pipeline-parallel deployments

Correctness never depends on a parameter resolving. The engine logs how many
parameters took each path at init.

CONFIGURATION                        *weight_transfer-m2n-index-configuration*

>python
    from vllm import LLM
    from vllm.config import WeightTransferConfig

    llm = LLM(
        model="my-model",
        weight_transfer_config=WeightTransferConfig(backend="nccl_m2n"),
    )
<
>bash
    vllm serve my-model --weight-transfer-config '{"backend": "nccl_m2n"}'
<

TRAINER SIDE                          *weight_transfer-m2n-index-trainer-side*

The trainer uses the stateful trainer engine. m2n plans each reshard from
the parameter's source layout, which a
|weight_transfer-base-index-2-parammeta-ownership-and-layout| declares on
its |vllm.distributed.weight_transfer.base.ParamMeta| (`owners`,
`mesh_shape`, `placements`), and sends what `iter_local()` yields: each
rank's local shard, never a `full_tensor()`.
|vllm.distributed.weight_transfer.base.ModuleSource| covers the common case:
it reads each parameter's device mesh and placements.

>python
    from vllm.distributed.weight_transfer import (
        ModuleSource,
        RayVLLMWeightSyncClient,
        WeightTransferTrainerFactory,
    )
    from vllm.distributed.weight_transfer.m2n_trainer import M2NTrainerInitInfo

    # Called on every trainer rank; rank 0 is the sender.
    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=M2NTrainerInitInfo(
            master_address=master_address,
            master_port=master_port,
            world_size=num_trainer_ranks + num_inference_workers,
            num_trainer_ranks=num_trainer_ranks,
            rank=my_rank,
        ),
        client=RayVLLMWeightSyncClient(llm_handle),
        source=ModuleSource(model),
    )

    # Each round, on every trainer rank:
    engine.send_weights()
<
`send_weights()` drives the whole round --- `start_weight_update`,
`update_weights`, `finish_weight_update`. Every rank in the communicator
must be inside the same reshard, so `update_weights` has to be in flight
while the trainer sends; the engine runs it on a helper thread so the
trainer loop does not have to open-code that.

Trainers with a custom producer (a Megatron export, MoE re-fusing) subclass
|vllm.distributed.weight_transfer.base.WeightSource|, declare each layout on
|vllm.distributed.weight_transfer.base.ParamMeta| and implement
`iter_local()`. A 1-D mesh is described over m2n's 2-D mesh with a size-1
second axis. Each yielded tensor must match its declared dtype and local
shape, and is kept alive in stream order until its reshard completes.

See `examples/rl/rlhf_m2n.py`
https://github.com/vllm-project/vllm/blob/main/examples/rl/rlhf_m2n.py for a
runnable FSDP → TP example.

LIMITATIONS                            *weight_transfer-m2n-index-limitations*

- vLLM validates tensor-rank and dtype support while agreeing on the
  complete plan; the installed M2N runtime validates them again for each
  reshard.
- No pipeline-parallel trainers. Every parameter must be owned by all
  trainer ranks, in rank order (`owners` unset or `(0, ..., T-1)`), with a
  1-D or 2-D mesh. Partitioned owners, such as one group per pipeline stage,
  are rejected at init.
- `Partial` placements cannot be sent as shards.
  |vllm.distributed.weight_transfer.base.ModuleSource| declares such a
  parameter replicated and gathers it in `iter_local()`.
- Models with known model-level checkpoint preprocessing use the full-tensor
  fallback for the affected module.
- A reshard cannot be issued from inside a CUDA graph capture (weight
  updates run outside capture, so this only matters for custom callers).
- vLLM checks every parameter's shard overlap against conservative 16-source
  and 64-target capacities before committing the plan. The installed M2N
  runtime remains authoritative and validates each reshard again.
- Each communicator holds a cached staging pool (~256 MiB by default: 4
  channels x 64 MiB).

ModelExpress Engine                  *vllm-weight_transfer-modelexpress-index*

The `modelexpress` weight transfer engine installs immutable weight versions
published through ModelExpress https://github.com/ai-dynamo/modelexpress.
Each update identifies the exact version to install, while ModelExpress
handles source selection, transfer, and installation.

                 *weight_transfer-modelexpress-index-when-to-use-modelexpress*
WHEN TO USE MODELEXPRESS

- Your workflow manages immutable weight versions through the ModelExpress
  Refit API.
- Inference workers need to pull a specific published version through
  ModelExpress, using GPU peer transfer or object storage.
- You want to load full checkpoints or replay checkpoint deltas from S3.

HOW IT WORKS                 *weight_transfer-modelexpress-index-how-it-works*

1. A publisher creates a weight-version resource through the ModelExpress
   Refit API, publishes its payload, and marks the version READY.
2. The orchestrator pauses generation and calls `start_weight_update` on the
   inference engine.
3. The orchestrator calls `update_weights` with the target `version_id`.
   Each worker's `ModelExpressGeneratorClient` resolves and stages that
   version, then applies it to the live vLLM model.
4. After a successful update, `finish_weight_update` releases the staged
   handle. The orchestrator can then resume inference.

Initialize the backend before starting an update session, and send exactly
one version per session. Invalid transitions must raise; an orchestrator
must keep inference paused after an update error and retry with a new
session only after cleanup. An error does not roll back weights that were
already applied.

`ModelExpressTrainerClient` is an optional publisher. Custom integrations
can manage weight-version resources directly through the ModelExpress
server's Refit API. For S3, create a STAGING version with the correct model,
payload format, lineage, and index URI; upload the index and referenced
shards in the format expected by `ModelExpressGeneratorClient`; then mark
the version READY. See the S3 Delta Weight Refit guide
https://github.com/ai-dynamo/modelexpress/blob/main/docs/S3_DELTA_WEIGHT_REFIT.md
for the publication sequence and generator artifact requirements.

vLLM's `modelexpress_engine.py` re-exports the engine and its init/update
dataclasses from
`modelexpress_rl.inference.engines.vllm.weight_transfer_engine`. The
implementation and configuration schema live in ModelExpress. Upgrading the
installed ModelExpress package and restarting workers picks up compatible
changes without a vLLM code change. The package must continue to implement
vLLM's |vllm.distributed.weight_transfer.base.WeightTransferEngine|
interface.

INFERENCE SIDE             *weight_transfer-modelexpress-index-inference-side*

  Development version: ~

  This backend currently uses unreleased ModelExpress features from `main`,
  which may introduce breaking changes. These features will be included in
  the official ModelExpress v0.8.0 release.

Install ModelExpress from the `main` branch on every worker:

>bash
    uv pip install "git+https://github.com/ai-dynamo/modelexpress@main#subdirectory=modelexpress_client/python"
<
The backend is registered natively and loaded only when selected;
`VLLM_PLUGINS=modelexpress` is not required for weight transfer. If the
plugin is enabled, it preserves the native registration and uses the same
engine implementation.

>python

    from vllm.config import WeightTransferConfig

    llm = LLM(model="my-model", weight_transfer_config=WeightTransferConfig(backend="modelexpress"))
<

NCCL Engine                                  *vllm-weight_transfer-nccl-index*

The NCCL weight transfer engine uses NCCL https://developer.nvidia.com/nccl
broadcast operations to transfer weights from the trainer to inference
workers. It supports multi-node and multi-GPU setups where the trainer and
inference engine run on separate GPUs.

WHEN TO USE NCCL                 *weight_transfer-nccl-index-when-to-use-nccl*

- Training and inference on separate GPUs (possibly across nodes)
- Tensor-parallel inference with multiple workers that all need the updated
  weights
- You need high-bandwidth, low-latency weight transfer over NVLink or
  InfiniBand

HOW IT WORKS                         *weight_transfer-nccl-index-how-it-works*

1. The trainer's broadcasting ranks and all inference workers join a shared
   NCCL process group using |vllm.distributed.utils.StatelessProcessGroup|
   (vLLM's torch.distributed-independent group abstraction). Trainer rank 0
   is group rank 0; with |weight_transfer-nccl-index-broadcasting-ranks|
   they take `[0, rank_offset)` and workers follow them (`rank_offset` is 1
   otherwise).
2. The trainer broadcasts weights to all workers simultaneously. Each worker
   receives and loads the weights.
3. Optionally, packed tensor broadcasting batches multiple small tensors
   into larger buffers with double/triple buffering and CUDA stream overlap
   for higher throughput. This implementation is based on
   NeMo-RL's packed tensor
   https://github.com/NVIDIA-NeMo/RL/blob/main/nemo_rl/utils/packed_tensor.py.

The workers' `update_weights` and the trainer's broadcast run at the same
time --- both sides rendezvous inside the same NCCL calls. The trainer
engine owns that concurrency internally.

INFERENCE SIDE                     *weight_transfer-nccl-index-inference-side*

The inference side takes a plain backend selector. The rendezvous parameters
and the packing wire params arrive from the trainer at the init handshake.

>python
    from vllm import LLM
    from vllm.config import WeightTransferConfig

    llm = LLM(model="my-model", weight_transfer_config=WeightTransferConfig(backend="nccl"))
<
>bash
    vllm serve my-model --weight-transfer-config '{"backend": "nccl"}'
<
Nothing else is required: `init_weight_transfer_engine`,
`start_weight_update`, `update_weights`, and `finish_weight_update` are all
driven remotely by the trainer engine.

TRAINER SIDE                         *weight_transfer-nccl-index-trainer-side*

>python
    from vllm.distributed.weight_transfer import (
        ModuleSource,
        HTTPVLLMWeightSyncClient,
        WeightTransferTrainerFactory,
    )
    from vllm.distributed.weight_transfer.nccl_engine import NCCLTrainerInitInfo

    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=NCCLTrainerInitInfo(
            master_address=master_address,
            master_port=master_port,
            world_size=world_size,   # broadcasting trainer ranks + all inference workers
            rank=0,                  # this trainer rank; rank 0 is the sender
            packed=True,
        ),
        client=HTTPVLLMWeightSyncClient("http://localhost:8000"),  # or RayVLLMWeightSyncClient(llm)
        source=ModuleSource(model),
    )

    engine.send_weights()   # once per sync
<
`trainer_init` drives the whole handshake: it kicks off the inference side's
`init_weight_transfer_engine` (through the client) on a side thread while
opening the trainer's own rank-0 endpoint, since both ends must rendezvous
together. It builds the worker's init info itself, with `rank_offset` set to
the number of broadcasting ranks (1 unless the source is partitioned) and
the same packed params, so the two sides cannot disagree.

`send_weights()` then drives `start_weight_update`, `update_weights` --- run
concurrently with the broadcast --- and `finish_weight_update`, and returns
only once every transfer has drained.

------------------------  -------  -------------------------------------------

world_size                ---        Transfer NCCL group size: the broadcasting
                                   trainer ranks plus the inference workers (1
                                   + num_workers for a single sender). Other
                                   trainer ranks are not counted
rank                      ---        Keyword-only. This trainer process's rank;
                                   0 is the sender

`packed` defaults to `True` here. The worker-side default is `False`, but it
only applies when no trainer ships a value --- which, on this path, never
happens.

                       *weight_transfer-nccl-index-packed-tensor-broadcasting*
Packed Tensor Broadcasting

When `packed=True`, weight tensors are packed into large contiguous buffers
before broadcasting. This cuts the number of NCCL operations and uses
double/triple buffering with dedicated CUDA streams to overlap packing,
broadcasting, and unpacking.

You set `packed`, `packed_buffer_size_bytes`, and `packed_num_buffers` only
on |vllm.distributed.weight_transfer.nccl_engine.NCCLTrainerInitInfo|. The
trainer propagates them to the worker inside `trainer_init`, the worker
records them at the handshake, and `receive_weights` decodes with exactly
the values the trainer encoded with. They are not per-round `update_weights`
fields.

  Memory: ~

  Each side holds a buffer of up to `packed_buffer_size_bytes` per rotating
  buffer, so up to `packed_buffer_size_bytes * packed_num_buffers` (2 GiB at
  the defaults); it is smaller for small transfers. On the trainer, each
  buffer starts at 64 MiB (or its first bytes, if more) and doubles as
  needed; while growing, the old buffer is briefly held too and may stay
  reserved by PyTorch's caching allocator. The workers size each receive
  buffer to its chunk. Lower `packed_buffer_size_bytes` if that is too much
  headroom. CPU-resident sources work but are copied synchronously, which is
  slower. A non-contiguous tensor split across chunks also needs a
  contiguous copy of its full size on the trainer while it is sent.

                *weight_transfer-nccl-index-metadata-and-iter_full-must-agree*
Metadata and `iter_full()` must agree

Dense NCCL builds the per-round update info from
|weight_transfer-base-index-2-weightsource| and ships it ahead of the bytes;
the worker sizes its receive buffers from that info, and in packed mode cuts
its chunk boundaries from it. The bytes themselves come from the source's
`iter_full()`.

If `iter_full()` disagrees with what `metadata` declared --- a reordered,
omitted, or re-dtyped parameter --- the two sides split the same byte stream
differently. The transfer then either hangs in NCCL waiting for a length
that never arrives, or loads garbage into the model.

The sender therefore checks each pair against the declared metadata as it
goes, one comparison per parameter, and raises naming the first divergent
parameter rather than letting it reach the wire.
|vllm.distributed.weight_transfer.base.ModuleSource| satisfies this by
construction. If you write a custom source --- a Megatron export, an MoE
re-fusing pass --- this is the invariant to test first.

Broadcasting ranks             *weight_transfer-nccl-index-broadcasting-ranks*

Each parameter is broadcast by its first owner (rank 0 when `owners` is
unset). When that is rank 0 for every parameter, rank 0 is the only
broadcaster. Other owners (FSDP peers of rank 0) only drive `iter_full()` to
take part in the gathers.

A partitioned source, such as pipeline stages declaring
`owners=(stage ranks...)`, has several broadcasters. They join the transfer
group at group ranks `[0, rank_offset)` in trainer-rank order, rank 0 always
included. Every rank derives this plan from `metadata`, which is identical
on every rank, so the broadcasters need no extra coordination. In
`send_weights()`, rank 0 sends one `update_weights` per broadcaster, in
order, each tagged with that broadcaster's group rank as `src`. Each
broadcaster sends its own parameters during its turn and receives and
discards the others' to stay in the collective. Initialize and call
`send_weights()` on every trainer rank concurrently.

Every parameter a rank owns must share its first owner, since each
broadcaster gathers and sends in its own turn. So with several broadcasters
every parameter must declare `owners`. Rank 0 is always in the transfer
group and only gathers in its own turn, so if it owns a parameter it must be
that parameter's first owner. `trainer_init` raises on every rank otherwise.

A failure on any broadcaster during an update is fatal for the transfer.
That rank raises immediately, but the other trainer ranks and the inference
workers can stay blocked in that update's broadcasts, so tear down the
trainer job and restart or re-initialize the inference engine before
transferring again.

`rlhf_nccl_multi_source.py`
https://github.com/vllm-project/vllm/blob/main/examples/rl/rlhf_nccl_multi_source.py
shows two pipeline stages updating one tensor-parallel inference engine.

                *weight_transfer-nccl-index-metadata-is-sent-once-then-reused*
Metadata is sent once, then reused

Every `update_weights` call needs the list of parameters it carries:
`names`, `dtype_names` and `shapes`. For a large model that list is long
(about 19,000 entries for Qwen3-30B-A3B), yet an RL trainer sends the same
parameters every round. So the worker remembers the list:

update_info you send                What the worker loads
----------------------------------  ------------------------------------------
names, dtype_names, shapes filled   Exactly these parameters. The worker also
in                                  saves this list.
All three lists empty (or {})       The list saved by the previous
                                    update_weights call on the same model from
                                    the same src.
All three lists empty, nothing      Nothing.
saved yet

Rules to remember:

- The first round must send the full list. After that, send empty lists
  whenever the parameters are the same as last round.
- Send the full list again whenever anything changes: a parameter added,
  removed, renamed, reordered, re-dtyped or reshaped. The worker does not
  check that empty-list rounds still match what the trainer sends; a
  mismatch hangs in NCCL or loads wrong values.
- The target model and the draft model keep separate lists. A
  `/start_draft_weight_update` round reuses only the draft's list.
- `init_weight_transfer_engine` clears every saved list, so the first round
  after a re-init must send the full list again.

`NCCLTrainerWeightTransferEngine.send_weights` follows these rules for you:
it compares `metadata` with what the last successful round sent, and sends
empty lists when they are equal. You only need to think about them if you
build `update_info` yourself, for example over HTTP without vLLM.

                   *weight_transfer-nccl-index-trainer-without-vllm-over-http*
TRAINER WITHOUT VLLM OVER HTTP

A trainer can speak the |training-weight_transfer-index-api-endpoints|
directly, with only PyTorch and an HTTP client. It mints the `ncclUniqueId`
itself and is NCCL rank 0. Reference: `rlhf_http_nccl_no_vllm.py`
https://github.com/vllm-project/vllm/blob/main/examples/rl/rlhf_http_nccl_no_vllm.py.

`POST /init_weight_transfer_engine` body `{"init_info": {...}}`:

Field                     Default  Meaning
------------------------  -------  -------------------------------------------
nccl_unique_id_b64        ---        Standard (not URL-safe) base64 of the
                                   128-byte ncclUniqueId. Replaces
                                   master_address / master_port
rank_offset               ---        First worker rank; 1 for one trainer rank
world_size                ---        Trainer ranks + GET /get_world_size
packed                    false    Packed broadcasting
packed_buffer_size_bytes  1 GiB    Must match the trainer's chunking
packed_num_buffers        2        Worker-side receive buffers

- Worker rank = `rank_offset + dp_index * (TP * PP) + rank`.
- `/init_weight_transfer_engine` returns only after all ranks join: send it
  in the background while the trainer calls
  `ncclCommInitRank(world_size, uid, 0)`. There is no timeout; if the
  trainer never joins, the workers wait forever.
- Right after init every worker issues a warm-up `all_reduce` (sum) of
  `torch.zeros(1)` (one float32 element). The trainer must issue the same
  one before any other collective.

Each sync: `POST /start_weight_update`, then `POST /update_weights` with
`{"update_info": {"names", "dtype_names", "shapes"}}` in the background
while rank 0 broadcasts in `names` order, then `POST /finish_weight_update`.
`dtype_names` are `torch` attribute names (`"bfloat16"`); `shapes` are full
checkpoint shapes. From the second sync on, send `{"update_info": {}}` if
the parameters did not change; see
|weight_transfer-nccl-index-metadata-is-sent-once-then-reused|. An optional
`src` (default `0`, below `rank_offset`) selects the trainer rank that
broadcasts that update, so one start/finish lifecycle can carry updates from
several trainer ranks.

- Unpacked: one broadcast per tensor.
- Packed: lay the tensors' `t.contiguous().view(-1).view(torch.uint8)` bytes
  out in `names` order as one stream, each tensor starting at a multiple of
  16, and cut it every `packed_buffer_size_bytes` (rounded down to 16); a
  tensor crossing a cut is split there; an empty tensor adds no padding.
  Broadcast each chunk as soon as it is full (or only alignment padding
  would fit), ending at its last byte, then the rest; a chunk of no bytes is
  not sent.

SPARSE NCCL                           *weight_transfer-nccl-index-sparse-nccl*

Sparse, flat-index weight patches use
`WeightTransferConfig(backend="sparse_nccl")`. Names, full shapes, and flat
indices are interpreted in checkpoint/Hugging Face coordinates. Every
inference rank receives the same checkpoint-global patch, then the model's
native `load_weights()` maps it to rank-local TP/EP and packed runtime
parameters.

Tensor parallelism is supported and does not have to match the trainer's
layout. Pipeline-parallel behavior is not covered by the current sparse NCCL
GPU test.

Sparse is a delta backend: each call supplies replacement patches rather
than a stable stream of the model's parameters. The engine therefore takes
no |vllm.distributed.weight_transfer.base.WeightSource|; patches go straight
to `send_weights(patches)`, and an empty patch list is a no-op.

>python
    from vllm.distributed.weight_transfer import (
        RayVLLMWeightSyncClient,
        WeightTransferTrainerFactory,
    )
    from vllm.distributed.weight_transfer.sparse_nccl_engine import (
        SparseNCCLTrainerInitInfo,
        SparseWeightPatch,
    )

    client = RayVLLMWeightSyncClient(llm)
    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=SparseNCCLTrainerInitInfo(
            master_address=master_address,
            master_port=master_port,
            world_size=world_size,
            rank=0,
        ),
        client=client,
    )

    patches = [
        SparseWeightPatch(
            name="model.layers.0.mlp.down_proj.weight",
            indices=flat_indices,           # int32, 1-D
            values=new_values,              # same length as indices
            full_shape=tuple(param.shape),  # required when sending via the engine
        )
    ]
    engine.send_weights(patches)
<
Each `send_weights(patches)` call owns a complete one-shot `start` /
`update` / `finish` lifecycle.

RL infrastructure that owns the generic worker lifecycle can keep one
logical update open across bounded chunks without adding trainer-side
session state:

>python
    client.start_weight_update()
    for patches in patch_chunks:
        engine.send_weight_chunk(patches)
    client.finish_weight_update()
<
Sparse NCCL sends only `O(nnz)` indices and values, in batches of at most
512 MiB (a larger patch travels alone). Workers validate and apply each
batch before receiving the next, so an invalid batch fails after earlier
ones landed. Checkpoint application still uses `O(N)` staging through the
native loader, and the caller owns export/diff state and restart or reseed
after a partial failure.

`rlhf_sparse_nccl.py`
https://github.com/vllm-project/vllm/blob/main/examples/rl/rlhf_sparse_nccl.py
demonstrates per-expert checkpoint patches with a Qwen3 MoE TP2/EP2 engine.

LIMITATIONS                           *weight_transfer-nccl-index-limitations*

- A broadcaster failure is fatal. See
  |weight_transfer-nccl-index-broadcasting-ranks|.
- Full tensors on the wire. Each broadcaster materializes its parameters in
  full and every worker receives all of it, whatever its tensor-parallel
  shard. For large or expert-parallel models, see
  |vllm-weight_transfer-sharded_rdt-index| or
  |vllm-weight_transfer-m2n-index|.
- Sparse NCCL's pipeline-parallel behavior is untested.

Sharded RDT Engine                    *vllm-weight_transfer-sharded_rdt-index*

The sharded RDT weight transfer engine moves weights point-to-point over
NIXL https://github.com/ai-dynamo/nixl using Ray Direct Transport (RDT),
Ray's zero-copy tensor transport between actors. It is pull-based: the
inference workers initiate every transfer and each one asks only for the
slice it consumes under tensor and expert parallelism. A large MoE model
therefore moves roughly `total_bytes / num_workers` per worker instead of
the `total_bytes` a broadcast costs.

                   *weight_transfer-sharded_rdt-index-when-to-use-sharded-rdt*
WHEN TO USE SHARDED RDT

- Very large models where broadcasting whole parameters is the bottleneck
  --- typically an MoE served with expert parallelism, where each worker
  owns a small fraction of the experts
- Trainer and inference on separate GPUs, over a fabric NIXL supports
  (InfiniBand, RoCE, EFA)
- Trainers that are themselves sharded, including pipeline-parallel ones
  where a rank holds only part of the model

Requirements:

- `distributed_executor_backend="ray"` --- the workers must be Ray actors
- Ray `>= 2.56.0` on both the trainer and the workers for GPU staging; host
  staging requires Ray `>= 2.58.0`
- `nixl` installed in the environment shared by trainer and workers

HOW IT WORKS                  *weight_transfer-sharded_rdt-index-how-it-works*

*weight_transfer-sharded_rdt-index-slices-are-tracked-through-vllms-own-weight-loaders*
Slices are tracked through vLLM's own weight loaders

A weight loader normally receives a full HF-format tensor and slices out the
part this worker needs. Instead of sending it one, the engine hands it a
|vllm.distributed.weight_transfer.sharded_rdt_fake.FakeRDTTensor|: a
zero-storage tensor that answers `.shape` / `.dtype` / `.size()` but holds
no data. Every view or slice op the loader calls returns a new fake with
that op appended to a recorded chain, and `copy_` is the sink that ends it.

That chain is the wire format.
`("model.layers.0.w", (("narrow", (0, 512, 512), ()), ("t", (), ())))` tells
the trainer: take this tensor, `narrow` it, transpose it, send the result.
The trainer replays it with `getattr(tensor, op)(*args, **kwargs)`.

Discovery is expensive, so it happens once, at `init_transfer_engine`, as a
dry run over `model.load_weights` with every parameter on meta. Nothing is
transferred; the engine just records, per leaf module, which slice feeds
which destination region. Every later sync is pure replay.

Anything a loader does that needs real data --- arithmetic, `.to()`,
`.float()`, `.item()`, `.data`, bool-mask indexing --- falls outside the
allowlist and raises at init. That is deliberate: failing loudly during
setup beats silently transferring the wrong bytes. `SUPPORTED_OPS` in
`sharded_rdt_common.py` is the single table both sides derive from, so the
recorder and the replayer cannot drift.

*weight_transfer-sharded_rdt-index-received-slices-land-directly-in-the-layerwise-reload-buffers*
Received slices land directly in the layerwise reload buffers

The engine drives |vllm-training-layerwise-index| itself, in
`start_weight_update` / `finish_weight_update`. Because the dry run already
recorded each destination as an `as_strided` region of its parameter, an
arriving slice is copied straight into the layer being reloaded --- no full
HF tensor is ever materialized on the worker, and no second pass over
`load_weights` runs. Each layer is quantized and copied into its persistent
kernel storage as soon as its last slice lands.

*weight_transfer-sharded_rdt-index-gathers-and-pulls-are-pipelined-which-is-what-gather_lookahead-bounds*
Gathers and pulls are pipelined, which is what `gather_lookahead` bounds

The trainer usually cannot serve its parameters as they sit: FSDP shards
them, and even an EP-split trainer has to assemble a whole expert. So each
sync still runs gather collectives --- but a layer at a time, not a model at
a time.

A gather group is one decoder layer. The parameter list is keyed on the
outermost index segment of each name, which leaves runs of un-indexed names
--- the embeddings before the first layer, the final norm and `lm_head`
after the last --- as groups of their own:

>text
    group 0     model.embed_tokens.weight
    group 1     model.layers.0.*          <- one decoder layer
    group 2     model.layers.1.*
    ...
    group N+1   model.norm.weight, lm_head.weight
<
The layer is the unit of everything that follows: the trainer gathers a
layer, publishes it (immediately pullable), and moves on to the next while
the consumers pull the one it just published. Once every consumer has
signalled that it is done with a layer, the trainer drops it and gains a
credit to gather another. `gather_lookahead` is how far ahead of the
consumers that loop may run, so at most `gather_lookahead + 1` layers are
resident on the trainer at a time. The default of 1 keeps the next layer
gathered and pullable while the current one is being pulled --- enough to
hide the handoff without doubling trainer memory. Raise it only if one
layer's gather is slower than its pulls.

Because a layer is also the unit the consumers free and the unit the receive
buffers are sized against, it is what keeps memory bounded on both sides:
without it the whole model would be one transfer, and both sides would have
to hold their full share of it at once. Keying on the index rather than a
fixed `model.layers.` prefix is what makes that hold across naming
conventions --- a VLM's `model.language_model.layers.`, GPT-2's
`transformer.h.`, a vision tower's `visual.blocks.`. The outermost index is
the one taken, which keeps a MoE layer whole
(`model.layers.3.mlp.experts.7.w1` keys on layer 3), and the partition
follows `metadata` order, so names sharing a layer index must be contiguous
there.

Ownership                        *weight_transfer-sharded_rdt-index-ownership*

A trainer rank need not hold the whole model. The source declares each
parameter's owners in
|weight_transfer-base-index-2-parammeta-ownership-and-layout|, the same on
every rank, so the engine builds the ownership table from metadata alone,
with no exchange at `trainer_init`. Each rank then iterates only the names
it owns, and the consumers route each pull to a rank that owns the name.
Pipeline stages, expert parallelism, and combinations of the two are all the
same declaration. Consumers spread their pulls across a name's owners, so no
single trainer NIC becomes the bottleneck. The producer-server name
all-gather at `trainer_init` also carries a digest of each rank's metadata,
so a rank whose metadata or owners differ fails at init.

*weight_transfer-sharded_rdt-index-receive-staging-and-concurrent-stage-streams*
Receive staging and concurrent stage streams

`staging_device` selects where each inference worker's receive slots live.
`"gpu"` (the default) receives directly into GPU memory. `"host"` uses host
memory that is page-locked with `cudaHostRegister` and registered with NIXL,
then enqueues the scatter into the model's GPU parameters asynchronously on
a CUDA stream. A slot is not reused until that asynchronous copy has
consumed it.

`stages_in_flight` (S) is the maximum number of independent, owner-connected
trainer stage streams a worker pulls from concurrently. The effective lane
count is `min(S, stream_count)`, with at least one lane, and each lane owns
`num_rdt_buffers` (K) slots. The receive-pool memory per worker is therefore
exactly:

>python
    min(S, stream_count) * K * rounded_slot_size
<
where `rounded_slot_size` is the largest packed chunk the worker pulls,
rounded up to a multiple of 256 MiB (or the `buffer_presize_gb` floor, if
larger). The pool is allocated in GPU memory for GPU staging. For host
staging each slot is pageable host memory of exactly `rounded_slot_size`
bytes, page-locked whole with `cudaHostRegister` and registered with NIXL;
torch's pinned allocator, which rounds every request up to a power of two
and caches freed blocks, is not involved, so the formula is the page-locked
footprint with no rounding caveat and no hidden host cache. Whenever a host
slot is dropped (on shutdown, on a regrow, or when a re-init replaces or
rolls it back) it is NIXL-deregistered and unregistered first, so its memory
returns to the system; a slot whose release fails at either step, or that a
post-processing thread which did not stop at shutdown may still be reading,
is kept page-locked and reported, never freed. Increasing S or K is an
explicit memory-for-throughput tradeoff and can exhaust the selected
allocator or the page-lockable memory; the engine reports the allocation or
registration failure, with the exact bytes it asked for, instead of silently
reducing concurrency, falling back to pageable memory or changing staging
modes.

A re-init builds its routing, plan and receive pool in a candidate and
commits it only once pre-registration and the post-processing worker have
started, so a failed attempt leaves the active state untouched and releases
only the slots it built itself. After the worker exists a re-init must keep
the pool geometry `(staging_device, lanes, K)`; it then reuses the active
slots. A slot is reused only after a two-stage wait: the generation
handshake (the worker's count of scatters done out of that slot reaches the
count queued, so the slot's read-done CUDA event has been recorded for this
use; the event binds only to its last record), then the event itself, which
proves the GPU read finished. On release paths the generation wait is
skipped when no worker is alive to publish the counts.

While other lanes have pulls in flight, a lane waiting for its slot's
previous scatter to finish rechecks the slot every 5 ms (`_SLOT_POLL_S`)
instead of blocking on it, so two replicas sharing a producer's packed slot
cannot wait on each other forever.

Sync 0 always runs serially with one lane and one pull in flight while both
endpoints finish registration. Pipelining starts with sync 1. The defaults,
`staging_device="gpu"` and `stages_in_flight=1`, preserve the existing GPU
path and issue, drain, and free order.

INFERENCE SIDE              *weight_transfer-sharded_rdt-index-inference-side*

>python
    from vllm import LLM
    from vllm.config import WeightTransferConfig

    llm = LLM(
        model="my-model",
        weight_transfer_config=WeightTransferConfig(backend="sharded_rdt"),
        distributed_executor_backend="ray",
    )
<
>bash
    vllm serve my-model \
      --distributed-executor-backend ray \
      --weight-transfer-config '{"backend": "sharded_rdt"}'
<
Everything else --- which producers exist, how the model splits into layer
groups, the ownership table --- arrives from the trainer at the init
handshake.

  Size the receive buffers before choosing gpu_memory_utilization: ~

  With GPU staging, each worker holds
  `min(stages_in_flight, stream_count) * num_rdt_buffers` receive buffers,
  each large enough for the biggest single slice batch it pulls. Like NCCL
  and NIXL internals, they do not count against `gpu_memory_utilization`, so
  a fraction that leaves no headroom can OOM during initialization even
  though model profiling succeeded. With the extensible KV cache (the
  default on CUDA and ROCm), `gpu_memory_utilization` defaults to 1.0 and
  the KV cache takes all memory left after warmup, so set it explicitly to
  leave room for these buffers (see
  |configuration-optimization-index-gpu-memory-utilization|). The buffer
  size is driven by the largest atomic slice --- for an untied vocab matrix
  on a worker that holds it unsliced, that is the whole embedding. Host
  staging moves this pool to host memory page-locked with `cudaHostRegister`
  and registered with NIXL, exactly
  `min(stages_in_flight, stream_count) * num_rdt_buffers * rounded_slot_size`
  bytes per worker, with the same sizing tradeoff.

TRAINER SIDE                  *weight_transfer-sharded_rdt-index-trainer-side*

>python
    from vllm.distributed.weight_transfer import (
        ModuleSource,
        HTTPVLLMWeightSyncClient,
        WeightTransferTrainerFactory,
    )
    from vllm.distributed.weight_transfer.sharded_rdt_trainer import (
        ShardedRDTTrainerInitInfo,
    )

    engine = WeightTransferTrainerFactory.trainer_init(
        init_info=ShardedRDTTrainerInitInfo(
            rank=rank,                                # rank 0 is the sender
            num_consumers=8,                          # inference workers, fleet-wide
            trainer_actor_namespace="my_namespace",   # must be visible to the workers
            staging_device="gpu",                     # "gpu" or "host"
            stages_in_flight=1,                       # concurrent stage streams
        ),
        client=HTTPVLLMWeightSyncClient("http://localhost:8000"),
        source=ModuleSource(model),
    )

    engine.send_weights()   # once per sync, on every trainer rank
<
`trainer_init` and `send_weights` run on every trainer rank: each one owns a
serve actor and takes part in the gathers, while only rank 0 drives the
inference-side handshake. Any
|weight_transfer-base-index-2-vllmweightsyncclient| works.

To adapt a trainer that is not a plain `nn.Module` --- a Megatron export, a
raw sharded checkpoint --- subclass
|weight_transfer-base-index-2-weightsource|.

LIMITATIONS                    *weight_transfer-sharded_rdt-index-limitations*

- Separate fleets only. The trainer and the inference workers run on
  different GPUs; colocated setups need |vllm-weight_transfer-ipc-index|.
- No EPLB. `enable_eplb=true` is rejected: it rearranges experts at runtime,
  which invalidates the recorded plan.
- Supported loader ops only. A weight loader that needs real data at init
  raises (see
  |weight_transfer-sharded_rdt-index-slices-are-tracked-through-vllms-own-weight-loaders|).
- Names that share a layer index must be contiguous in `metadata` order.

EXAMPLES                          *weight_transfer-sharded_rdt-index-examples*

- Small MoE on 4 GPUs
  https://github.com/vllm-project/vllm/blob/main/examples/rl/rlhf_sharded_rdt_small_ep.py

to one.
