Prepare Data for Post-Training                 *verl-preparation-prepare_data*

Last updated: 11/02/2026.

Before starting the post-training job, we need to prepare the data for the
policy training. The default loading path uses parquet files. For V1 PPO, a
|examples-config-custom-ppo-dataloader| can instead supply batches directly
from an existing loading pipeline.

We provide several data preprocess scripts for different datasets, including
GSM8K, MATH, HelloSwag, Full_hh_rlhf. To prepare other datasets, we need to
follow the following steps: The data preprocess script can be divided into
two parts:

1. The first part is the common part, which loads the dataset from
   huggingface's `datasets` package. Then preprocess the datasets with the
   `make_map_fn` and then store in the parquet format.

2. The users are required to implement the `make_map_fn()` function (as well
   as the `extract_solution`) on their own to support different datasets or
   tasks.

We already implemented the data preprocess of GSM8k, MATH, Hellaswag and
Full_hh_rlhf datasets. And we take the GSM8k dataset as an example:

GSM8K

In the `make_map_fn`, each data field should consist of the following 5
fields:

1. `data_source`: The name of the dataset. To index the corresponding reward
   function in the `RewardModel`
2. `prompt`: This field should be constructed in the format of huggingface
   chat_template. The tokenizer in `RLHFDataset` will apply chat template
   and tokenize the prompt.
3. `ability`: Define the task category.
4. `reward_model`: Currently, we only utilize the `ground_truth` field
   during evaluation. The `ground_truth` is computed by the
   `extract_solution` function. NOTED that the implementation of the
   corresponding reward function should align with this extracted
   `ground_truth`.
5. `extra_info`: Record some information of the current prompt. Not use for
   now.

>python
    def extract_solution(solution_str):
        solution = re.search("#### (\\-?[0-9\\.\\,]+)", solution_str) # extract the solution after ####
        assert solution is not None
        final_solution = solution.group(0)
        final_solution = final_solution.split('#### ')[1].replace(',', '')
        return final_solution

    instruction_following = "Let's think step by step and output the final answer after \"####\"."

    # add a row to each data item that represents a unique id
    def make_map_fn(split):

        def process_fn(example, idx):
            question = example.pop('question')

            question = question + ' ' + instruction_following

            answer = example.pop('answer')
            solution = extract_solution(answer)
            data = {
                "data_source": data_source,
                "prompt": [{
                    "role": "user",
                    "content": question
                }],
                "ability": "math",
                "reward_model": {
                    "style": "rule",
                    "ground_truth": solution
                },
                "extra_info": {
                    'split': split,
                    'index': idx
                }
            }
            return data

        return process_fn

Implement Reward Function for Dataset       *verl-preparation-reward_function*

Last updated: 11/12/2026.

For each dataset, we need to implement a reward function or utilize a reward
model to compute the rewards for the generated responses. We already
pre-implemented some reward functions in reward_score directory
https://github.com/verl-project/verl/blob/main/verl/utils/reward_score. You
can also use customized reward functions.

Currently, we support reward functions for GSM8k, MATH, DAPO-Math,
Math-Verify, PRIME math/code, Geometry3K, and Search-R1 QA datasets. For
RLHF datasets (e.g., full_hh_rlhf) and Code Generation (e.g., APPS), we
utilize reward model and SandBox for evaluation respectively.

REWARDMANAGER                      *preparation-reward_function-rewardmanager*

In the entrypoint of the PPO Post-Training script main_ppo.py
https://github.com/verl-project/verl/blob/main/verl/trainer/main_ppo.py#L33,
we implement a `RewardManager` that utilize pre-implemented reward functions
to compute the scores for each response.

In the `RewardManager`, we implemented a `__call__` function to compute the
score for each response. All the reward functions are executed by
`compute_score_fn`. The input is a `DataProto`, which includes:

- `input_ids`, `attention_mask`: `input_ids` and `attention_mask` after
  applying chat_template, including prompt and response
- `responses`: response tokens
- `ground_truth`: The ground truth string of the current prompt. Stored in
  `non_tensor_batch` in the `DataProto`, which should be preprocessed in the
  parquet files.
- `data_source`: The dataset name of the current prompt. Stored in
  `non_tensor_batch` in the `DataProto`, which should be preprocessed in the
  parquet files.

After detokenize the responses, the responses string and the ground truth
string will be input to the `compute_score_fn` to compute the score for each
response.

REWARD FUNCTIONS                *preparation-reward_function-reward-functions*

Pre-implemented                  *preparation-reward_function-pre-implemented*

We already pre-implemented some reward functions in reward_score directory
https://github.com/verl-project/verl/blob/main/verl/utils/reward_score.

- In the GSM8k example
  https://github.com/verl-project/verl/blob/main/verl/utils/reward_score/gsm8k.py
  (`gsm8k`), we force the response to output the final answer after four
  `####`, then use string matching to compare with the ground truth.
- In the MATH example
  https://github.com/verl-project/verl/blob/main/verl/utils/reward_score/math_reward.py
  (`math_reward`), we follow the implementation in
  lm-evaluation-harness repository
  https://github.com/EleutherAI/lm-evaluation-harness/blob/main/lm_eval/tasks/hendrycks_math/utils.py.
- Additional built-in presets include `math_dapo`, `math_verify`,
  `prime_math`, `prime_code`, `geo3k`, `search_r1_like_qa_em`, and
  `search_r1_like_qa_subem`.

*preparation-reward_function-selecting-a-fallback-preset-via-cli-without-modifying-parquet-files*
Selecting a Fallback Preset via CLI without Modifying Parquet Files

By default, `default_compute_score` dispatches to a built-in preset based on
each row's `data_source` column. When using a public Parquet file whose
`data_source` is not in the built-in table (for example, `"dapo_filter"` or
sub-source tags such as `"MATH##Aops"`), you can set
`reward.preset=<preset_name>` directly on the command line without editing
the Parquet file:

- `reward.preset=<preset_name>` sets the fallback preset for any unmapped
  `data_source` while keeping built-in `data_source` mappings (such as
  `openai/gsm8k` or `aime*`) intact for multi-dataset validation.

>bash
    # Use math_dapo as the fallback preset for unmapped data_source values (e.g. dapo_filter or MATH##Aops)
    python3 -m verl.trainer.main_ppo ... reward.preset=math_dapo

Customized                            *preparation-reward_function-customized*

You can implement customized reward functions in a separate file and specify
them using `reward.custom_reward_function.path` and
`reward.custom_reward_function.name`. For the set of them, please refer to
|examples-config-config-explain-page|.

The parameters of your reward function should be `data_source`,
`solution_str`, `ground_truth`, and `extra_info`. For example:

>python
    def my_reward_fn(data_source, solution_str, ground_truth, extra_info=None):
      return len(solution_str)/100
<
If you are testing only a single customized reward function, you can simply
name it ‘compute_score' and leave `reward.custom_reward_function.name`
unset.

To run multiple tests with different customized reward functions, you can
modify both `reward.custom_reward_function.path` and
`reward.custom_reward_function.name` for each trial. For instance, you might
create a single my_reward.py file and implement multiple reward functions
within it. This way, for different trials, you only need to adjust
`reward.custom_reward_function.name`, making it more convenient to conduct
multiple tests within scripts.
